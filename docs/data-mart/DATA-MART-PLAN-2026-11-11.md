# Единая витрина данных: карта, решения и план (11.11.2026)

Цель: одна сквозная витрина, куда попадают все данные и откуда **весь** продукт (Главная, «Продажи», «Изделия», «Маржа», Cashflow, Excel, окна отчётов) читает одни и те же готовые числа. Цепочка: **сырьё (лот) → закупка и оплаты → ТЗ (списание + работа) → изделие (артикул · цвет · размер) → получено → продано → остаток → деньги**, в обе стороны.

## 0. Решения владельца (11.11.2026)

- **Курс 110 — только когда образуется розничная цена продажи.** До этого курс указан в документах закупки или рассчитывается как отношение рублёвых затрат к валютным. Закупка и себестоимость живут в рублях (и в $ с фактическим курсом закупки); 110 применяется на розничной стороне и при сверке с отчётом (SC EUR × 110).
- **Себестоимость: сначала по партии, затем средневзвешенная, видны обе** (`DmCostParty` и `DmStock.unitCostAvgRub`). Сопоставление цвета и размера ТЗ с изделием отчёта пока на уровне модели (помечено `estimated`), следующий шаг — сопоставление по цвету и размерам.
- **Размер обязателен** в ключе изделия (артикул · цвет · размер).
- Расхождения источников показываем явно (`dm_checks`), штуки берём из отчёта, даты из файла.
- Хранение: таблицы в той же PostgreSQL (`Dm*`), пересборка `scripts/mart-refresh.ts`.

## 4. Прототип сквозной цепочки (скрипт `scripts/trace-article-chain.ts`)

Прогон по четырём артикулам (файлы `trace-*.md` рядом). Что показал:

- **M002:** 5 ТЗ → 49 лотов меха (570 шкур, 17,2 млн ₽) из 5 аукционов → получено 6 → продано 3 → остаток 3 (прайс 49,17 млн ₽). Штуки в ТЗ, файле и отчёте сходятся; закупка по ТЗ 3 395 671 ₽/изд. против 3 558 207 ₽ по отчёту (−4,6 %).
- **M026 (кириллическая «М»):** связь работает через нормализацию кода; закупка по ТЗ и отчёту сходится (0,5 %).
- **M041:** закупка по ТЗ 390 344 ₽ и по отчёту 390 344 ₽ — **совпадает до рубля**. Значит отчёт поставщика строится от той же стоимости ТЗ (курс 110), и витрина может считать закупку из цепочки, а отчёт использовать как контроль.
- **MH-02:** ТЗ 19, файл прихода 19 (февраль 2026), отчёт 0 — цепочка рвётся именно в отчёте. Витрина должна показывать такой случай как «расхождение источников», а не молча брать один из них (остаток −2).

## 5. Целевая модель витрины

Таблицы-представления (read model), пересобираются одним заданием при любой загрузке данных:

1. `dm_sku` — изделие: артикул · цвет · размер, код модели (нормализованный, латиница, с дефисом), вид меха, категории.
2. `dm_sku_season` — по сезонам: заказано, получено, продано (товар сезона и календарь), закупка в €, NS, скидка.
3. `dm_movement` — датированные движения (приход, продажа, возврат) из строк файла.
4. `dm_lot` — лот сырья: закупка, аукцион, курс, сборы, стоимость в ₽ и €, остаток, оплаты (доля аукциона).
5. `dm_tz` и `dm_tz_lot` — ТЗ, их списания (лот → ТЗ), работа, расходы, вид меха и подкладка.
6. `dm_cost` — закупка единицы изделия: из цепочки ТЗ, с сверкой с SC EUR × 110.
7. `dm_stock` — остаток по изделию: штуки, закупка, розница по прайсу размера.
8. `dm_checks` — контрольные суммы и расхождения (845 / 637 / 291 / 346, ТЗ ↔ файл ↔ отчёт по артикулам).

Экраны читают только эти таблицы. Формулы (остаток, наценка 110, SO, курс) живут в одном месте.

## 6. План по шагам

1. **Карта и прототип** — сделано (этот документ и скрипт).
2. **Ядро витрины и контрольные суммы:** `dm_sku`, `dm_sku_season`, `dm_movement`, `dm_stock`, `dm_checks` в одном слое `src/lib/mart/`, с тестами на эталон (845 / 637 / 291 / 346, закупка остатка 1 569 840 €, розница 689 484 200 ₽).
3. **Перевод экранов по одному:** Главная («Активы», «Продажи и остатки»), «Продажи», «Изделия», «Маржа», Cashflow; после каждого — сверка и удаление старой считалки.
4. **Сквозная часть:** `dm_lot`, `dm_tz`, `dm_cost`; переходы вверх и вниз (изделие → ТЗ → лоты → закупка → оплаты и обратно).
5. **Единая загрузка:** отчёт, УПД, платежи, прайс — одна точка входа, после неё автоматически пересборка и проверки.
6. **Демо:** пересборка витрины входит в `scripts/rebuild-demo.sh`.

Критерий готовности каждого шага: цифры экрана равны витрине, витрина равна эталону, расхождения источников видны в `dm_checks`, а не скрыты.

## 7. Открытые вопросы

- Единый ключ изделия: нормализация кодов (кириллица/латиница, «MH02»/«MH-02»), номера лотов («СП0926-4» против «6»).
- Распределение меха на изделия: лот → ТЗ есть, ТЗ → размеры отчёта напрямую нет (нужна привязка ТЗ к строкам отчёта).
- Товар до FW25 (3 шт. продано без прихода в отчёте): как показывать.
- Курс: 110 до тех пор, пока не подтянется курс из документов закупки.
- Незавершённое производство (208 шт.): включать ли в активы и как считать затраты.
- Оплаты по аукциону целиком — как распределять на лоты и изделия.

## 9. Сопоставление ТЗ с изделиями (11.11, вечер)
Партии ТЗ привязаны к изделию отчёта (модель · цвет · размер): цвета через ColorRef + синонимы (TORTOR, VIOLET, BORDEAUX, ORANGE), размеры из строк ТЗ (повтор = штуки, «единый размер» → NS), запасной путь размер → цвет → модель. Результат: по размеру 44 %, по цвету 4 %, по модели 52 % штук. Закупка остатка по ТЗ 156,5 млн ₽ против 172,7 млн ₽ по отчёту (−9,4 %): расхождение не от сопоставления, а от разной базы себестоимости (ТЗ с работой и 4 % против SC EUR × 110). Контрольные суммы 845/637/291/346/689 484 200 сходятся. Нужен разбор с владельцем: какая себестоимость считается эталонной.

## 10. Решение владельца (11.11): эталоны
Себестоимость — строго по ТЗ (партия, затем средневзвешенная). Розничные цены — из присланного отчёта/прайса по размерам. Закупка по отчёту (SC EUR × 110) остаётся только справкой (check costAvgVsReport = info, −8,6 %). Изделиям без своей партии даётся средняя ТЗ по модели с пометкой.

## 11. Единый ключ изделия, синонимы цветов, прайс и журнал загрузок (11.11, ночь)
- Ключ изделия `skuKey` = АРТИКУЛ|ЦВЕТ канонический|РАЗМЕР (по модели ключ склеивал разные артикулы, поэтому ключ по артикулу). 338 изделий — 338 уникальных ключей.
- `DmColorAlias`: любое написание цвета → канонический цвет (справочник ColorRef + 4 ручных + 4 «auto», не найденных в справочнике: MAHOGANY, SILVER, ТОНИРОВКА, TONIROVKA).
- `DmRetailPrice`: розничный прайс из JSON разложен в таблицу по ключу изделия (298 строк); 2 строки без изделия в отчёте (M015/MINK SHARED W · БЕЛЫЙ · 44) — вынесено в проверку.
- `DmMovement.colorKey` = МОДЕЛЬ|ЦВЕТ (в файле приходов нет размера и полного артикула): все 605 движений связаны с изделиями.
- `DmLoad`: журнал загрузок (отчёт по размерам, прайс, строки приходов/продаж, партии ТЗ — версия источника, дата, строк).
- Проверки: повторы ключа 0 (ok), прайс без изделия 2 (warn), движения без изделия 0 (ok).
