# Единая витрина данных: карта, решения и план (11.11.2026)

Цель: одна сквозная витрина, куда попадают все данные и откуда **весь** продукт (Главная, «Продажи», «Изделия», «Маржа», Cashflow, Excel, окна отчётов) читает одни и те же готовые числа. Цепочка: **сырьё (лот) → закупка и оплаты → ТЗ (списание + работа) → изделие (артикул · цвет · размер) → получено → продано → остаток → деньги**, в обе стороны.

## 0. Решения владельца (11.11.2026)

- **Курс 110 — только когда образуется розничная цена продажи.** До этого курс указан в документах закупки или рассчитывается как отношение рублёвых затрат к валютным. Закупка и себестоимость живут в рублях (и в $ с фактическим курсом закупки); 110 применяется на розничной стороне и при сверке с отчётом (SC EUR × 110).
- **Себестоимость: сначала по партии, затем средневзвешенная, видны обе** (`DmCostParty` и `DmStock.unitCostAvgRub`). Сопоставление цвета и размера ТЗ с изделием отчёта пока на уровне модели (помечено `estimated`), следующий шаг — сопоставление по цвету и размерам.
- **Размер обязателен** в ключе изделия (артикул · цвет · размер).
- Расхождения источников показываем явно (`dm_checks`), штуки берём из отчёта, даты из файла.
- Хранение: таблицы в той же PostgreSQL (`Dm*`), пересборка `scripts/mart-refresh.ts`.

## 5. Целевая модель витрины

Таблицы-представления (read model), пересобираются одним заданием при любой загрузке данных:

1. `dm_sku` — изделие: артикул · цвет · размер, код модели (нормализованный, латиница, с дефисом), вид меха, категории.
2. `dm_sku_season` — по сезонам: заказано, получено, продано (товар сезона и календарь), закупка в €, NS, скидка.
3. `dm_movement` — датированные движения (приход, продажа, возврат) из строк файла.
4. `dm_lot` — лот сырья: закупка, аукцион, курс, сборы, стоимость в ₽ и €, остаток, оплаты (доля аукциона).
5. `dm_tz` и `dm_tz_lot` — ТЗ, их списания (лот → ТЗ), работа, расходы, вид меха и подкладка.
6. `dm_cost` — закупка единицы изделия: из цепочки ТЗ, с сверкой с SC EUR × 110.
7. `dm_stock` — остаток по изделию: штуки, закупка, розница по прайсу размера.
8. `dm_checks` — контрольные суммы и расхождения (845 / 637 / 291 / 346, ТЗ ↔ файл ↔ отчёт по артикулам).

Экраны читают только эти таблицы. Формулы (остаток, наценка 110, SO, курс) живут в одном месте.

4. **Сквозная часть:** `dm_lot`, `dm_tz`, `dm_cost`; переходы вверх и вниз (изделие → ТЗ → лоты → закупка → оплаты и обратно).
5. **Единая загрузка:** отчёт, УПД, платежи, прайс — одна точка входа, после неё автоматически пересборка и проверки.

Критерий готовности каждого шага: цифры экрана равны витрине, витрина равна эталону, расхождения источников видны в `dm_checks`, а не скрыты.

## 15. Курс 110 только для маркапа (12.11)
Закупка в рублях берётся только из ТЗ (они в рублях). Закупка из отчёта остаётся в евро (`unitCostReportEur`, `stockCostReportEur`), в рубли не переводится; сравнение «€ × 110 против ТЗ» убрано, `unitCostReportRub` обнулён. Курс 110 используется только в представлениях `vDmMarkupSold` ((NS RUR + Discount RUR) ÷ 110 ÷ SC EUR) и `vDmMarkupStock` (розница ÷ 110 ÷ закупка €).

## 16. Маркап = розница ÷ себестоимость по ТЗ (12.11)
Решение владельца: маркап = розничная цена (если она есть) ÷ себестоимость; всё в рублях, курс 110 не нужен. `vDmMarkupStock`: цена прайса ÷ себестоимость единицы по ТЗ (остаток: розница 690 млн ₽ ÷ себестоимость 158 млн ₽ = 4,15 по 170 изделиям с ценой). `vDmMarkupSold`: розница проданных штук до скидки (NS RUR + Discount RUR) ÷ себестоимость этих штук по ТЗ (FW25/26 3,27 · SS26 3,24 · FW26/27 4,24; итого около 3,56 против 3,68 по прежней формуле через 110 и евро). 3 проданные штуки без ТЗ в расчёт не входят. Открыт вопрос: розница с НДС или без?

## 17. Правила маркапа и средневзвешенного (12.11)
- Продано: (NS RUR + Discount RUR) ÷ себестоимость проданных штук по ТЗ. Остаток: розничная цена (если есть) ÷ себестоимость по ТЗ.
- Нет закупочной вообще → маркапа нет, изделие не участвует в средневзвешенном ни в числителе, ни в знаменателе (`vDmMarkupSoldWeighted`, `vDmMarkupStockWeighted` берут только строки с себестоимостью; в проверках `noCostSold`, `noCostStock`).
- Итоговые: продано 3,58 (288 шт. с закупочной), остаток 4,15 (339 шт.); FW25/26 3,27 · SS26 3,24 · FW26/27 4,24.

## 20. Размеры из прихода, а не из ТЗ (12.11)
Правило владельца: размеры в ТЗ условные, фактически приходит нужный размер; если пришло меньше, остаются размеры ТЗ, если пришло — размеры из прихода. Реализация: каждая партия заполняет только полученные штуки отчёта (ёмкость = получено): 1) тот же цвет и размер, 2) тот же цвет, другой размер, 3) любая полученная штука модели с незакрытым остатком; лишние единицы ТЗ (не пришедшие) остаются без изделия. Сначала завершённые ТЗ, затем ТЗ в работе (подхватывают приход сверх завершённых). Результат: M022 BLACK 44 получает вторую единицу Navy 44 (ТЗ 54) = 249 963 ₽ (уровень «модель»); M044 BROWN 46 = ТЗ 202 в работе, 561 878 ₽. «Средней по модели» с остатком больше нет; без закупочной остаётся только MH-07/SABLE NATURAL. Закупка остатка по ТЗ 165,8 млн ₽.

## 21. MH-07: закупочная как в карточке (12.11)
Решение владельца: у MH-07/SABLE NATURAL закупочная есть — берётся та, что в карточке артикула: ТЗ 75 (4 шт.) и ТЗ 182 (6 шт.) = 85 564 ₽ на 10 шт. = 8 556 ₽ на изделие (одна работа: мех из остатков не списан). Теперь без закупочной изделий нет. Маркап по MH-07 (продано): 15,08 и 7,54 (розница 129 000 ₽ на 8 556 ₽), в средневзвешенное входит; итог: продано 3,56 (291 шт.), остаток 4,16.

## 22. Статус по приходу, а не по ТЗ (12.11)
Правило владельца: приехало значит есть (статус ТЗ не важен); не приехало значит в работе, даже если ТЗ есть, и товар, на который ТЗ ещё нет, тоже в работе. В массиве: `vDmInWork` (заказано − получено по изделию и сезону); проверки `inWork` = 208 шт. (845 − 637), из них под ТЗ 131 (единицы ТЗ без прихода), без ТЗ 77. ТЗ в работе по полученному товару (М044 ТЗ 202, M030 ТЗ 198, M054 ТЗ 195) считаются полученными: себестоимость берётся в остаток.
