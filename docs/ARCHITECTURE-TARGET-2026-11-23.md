## 2. Главные проблемы (с доказательствами)

1. **Нет слоя между экраном и базой.** 150 файлов в `src/app` обращаются к Prisma напрямую, ещё 80 в `src/lib`. Страница = запросы + формулы + разметка в одном файле.
2. **Одни и те же числа считаются в нескольких местах.** Сегодня нашли четыре разных «долга по сырью», два определения «оплачено на аукционах», разные «Куплено» на Главной и в «Закупках» (шкуры подрядчика, Рысь, услуги по УПД, переплата подкладки). Каждый раз причина одна: формула живёт в нескольких экранах.
3. **Деньги, НДС, надбавка 4 %, переплаты не оформлены как единая модель.** Режимы «С НДС / 4 % / год / источник» реализованы в cookie и в разметке, правила расходятся между страницами.
4. **Витрина данных была кэшем, а не первичным источником.** Сделан первый этап (лоты, закупки, оплаты, полосы итогов), но Главная, «Оплаты», подтверждения, Производство и Cashflow считаются отдельно.
5. **Фоновая пересборка живёт в памяти процесса** (`setTimeout` в `mart/schedule.ts`): не переживает перезапуск, не работает при нескольких инстансах.
6. **Мультиарендность вручную.** `organizationId` добавляется в каждый запрос руками; один забытый фильтр = утечка данных между организациями.
7. **Тесты привязаны к живым данным.** Эталоны (617 штук, 7 495 756 ₽) устаревают при каждой загрузке отчёта; 10 тестов падают из-за данных или файлов на машине.
8. **Огромные файлы действий и страниц** тяжело читать, трудно тестировать, легко сломать при правке.
9. **Файлы на локальном диске** (`uploads/`), а не в объектном хранилище; Render и демо от этого зависят.

## 3. Целевая схема (монолит, слои)

```
UI (страницы, компоненты)         только собирают готовые модели, режимы показа берут из одного модуля
   │
Приложение (use-cases)            «принять закупку», «изменить лот», «внести оплату»: транзакция + событие + журнал
   │            │
Домен (чистые функции)            деньги (Decimal), НДС, надбавка 4 %, переплаты, зачёты — без Prisma, 100 % тестируется
   │
Данные (репозитории)              единственное место доступа к Prisma, всегда с организацией (tenant guard / RLS)
   │
Витрина (read-model Dm*)          события → инкрементальный пересчёт → нормализованные таблицы; экраны читают только их
   │
Очередь задач (Postgres)          пересборка витрины, импорты, письма; переживает перезапуск
```

Принципы:
- **Одна формула — одно место.** Домен считает, витрина хранит, экран показывает. Экран ничего не пересчитывает.
- **Запись и чтение разделены.** Запись идёт через use-case и пишет событие; чтение — из витрины.
- **Режимы показа** (год, НДС, 4 %, источник) — один модуль, у каждой страницы декларация, какие режимы она поддерживает.
- **Монолит остаётся.** Для одной команды и ~140 тыс. строк микросервисы не нужны.

## 5. Что не делать

- Не переписывать с нуля.
- Не дробить на микросервисы и не уходить с PostgreSQL.
- Не добавлять новые расчёты в страницы: сначала домен и витрина.

## 6. Решения, которые нужны от владельца

1. Определения (одно на всё приложение): что входит в «Куплено», «Оплачено», «Долг» (шкуры подрядчика, услуги по УПД, заказано-не получено, зачёт переплат).
2. Нужна ли работа нескольких организаций в одной базе (от этого зависят tenant guard и RLS).
3. Приоритет разделов для переноса на витрину (по умолчанию: «Оплаты», подтверждения, Главная).
