# Сохранность данных в «MVST FUR PRODUCTIONе»

Простыми словами: где лежат данные, что может пропасть, чем это защищено и как всё вернуть. Читать тем, кто тестирует и вносит правки.

## 1. Где что хранится

| Что | Где | Как не потерять |
|---|---|---|
| Все записи (закупки, лоты, ТЗ, оплаты, справочники, пользователи) | База PostgreSQL в Docker. Хранилище — именованный том `fur-erp_fur_erp_db_data` | Копия базы: `scripts/backup.sh` (ноутбук) или `sh deploy/backup.sh` (сервер) |
| Загруженные файлы (документы закупок, платёжки, фото примерок) | Папка `uploads/` на ноутбуке; на сервере — том `fur-erp_fur_erp_uploads`. В базе хранится только относительный путь (`purchase-docs/…`) | Те же скрипты копий кладут рядом архив файлов |
| Журнал изменений (кто, когда и что изменил, снимок до правки) | Таблица в той же базе, страница «История» (`/history`) | Попадает в копию базы вместе со всем остальным |
| Копии | Ноутбук: `~/Backups/fur-erp` (30 последних). Сервер: `~/backups/fur-erp` (14 последних) | Раз в неделю копируйте их ещё и на другой компьютер/диск — копии на том же диске не спасут при поломке диска |

Ссылки на документы Google Drive — это только ссылки: сами файлы на Диске приложение не трогает.

## 2. Что исчезает при каких действиях

В обычном интерфейсе нельзя удалить закупку, лот, ТЗ, партию, поставщика, клиента и организацию — их можно только отменить или отключить. Это сделано специально. Удаляются только «мелкие» записи; вот что уходит вместе с ними:

| Действие в программе | Что пропадёт вместе с записью |
|---|---|
| Удалить позицию закупки (только черновик) | Сама позиция; расчёт закупки пересчитается |
| Удалить расход закупки / ТЗ | Сам расход; себестоимость пересчитается |
| Удалить оплату закупки, аукциона, аванс | Запись об оплате и **прикреплённые к ней документы** (записи Drive; сами файлы на Диске остаются; файл-платёжка, загруженная в приложение, удаляется, если на неё больше никто не ссылается). Долг поставщику вырастет |
| Удалить оплату производства | Оплата, её разнесение по ТЗ и **прикреплённые документы**. Расчёты по всем ТЗ, которые она покрывала, пересчитаются |
| Удалить списание сырья в ТЗ | Строка списания; сырьё возвращается в лот |
| Удалить документ («Убрать») | Запись документа; загруженный файл — если на него никто не ссылается |
| Удалить позицию плана заказа | Позиция и её размеры; события календаря остаются, связь с позицией обнуляется |
| Удалить событие календаря, примерку, фото примерки, столбец «свои поля» | Само событие / примерка с фото (файлы удаляются навсегда) / значения столбца у всех лотов |
| Объединить цвета, виды меха, артикулы | «Лишняя» запись исчезает, все её строки переходят к основной. Нормы расхода «лишнего» артикула, которые уже есть у основного, отбрасываются |
| Удалить цвет или вид меха | Только пустой (нигде не используется) — иначе программа откажет и предложит объединить |

Если запись на что-то ссылается, база не даст её убрать «в обход» (поставщик, склад, материал, модель, статья расходов защищены от удаления, пока есть зависимые записи).

## 3. Что защищает

- **Подтверждения.** Каждая кнопка «Удалить / Убрать / Откатить / Объединить / Списать» спрашивает подтверждение и называет последствия.
- **Блокировки.** Принятую закупку, ТЗ со списаниями, использованный цвет и вид меха удалить нельзя; у принятой закупки нельзя удалять позиции и менять шапку.
- **Защита от чужой перезаписи.** Если двое открыли одну запись (закупку, позицию, ТЗ, оплату, модель), а один уже сохранил, второй получит сообщение «Запись изменил другой пользователь… обновите страницу» вместо тихой перезаписи.
- **Ввод не стирается.** Если сервер отклонил форму, поля остаются как были. План заказа сам сохраняет черновик в браузере и предупреждает при закрытии вкладки с несохранёнными данными.
- **Транзакции.** Приёмка закупки, завершение ТЗ, разнесение оплат, объединения справочников выполняются «всё или ничего».
- **Журнал изменений (страница «История»).** Хранит, кто и когда менял или удалял запись, и снимок значений до правки — по нему можно вручную восстановить стёртое.
- **Копии базы и файлов** и проверка миграций перед обновлением (`scripts/check-migration-safety.sh`).

## 4. Как восстановить из копии

Сначала решите, что именно нужно вернуть.

**Случай А. Удалили или испортили одну-две записи.** Не восстанавливайте всю базу. Откройте «История», найдите запись, возьмите значения из снимка «до» и внесите заново вручную. Если в истории нет снимка — сделайте шаг Б (в отдельную базу) и посмотрите там.

**Случай Б. Посмотреть копию, ничего не ломая (отдельная пробная база).** Ноутбук:
```bash
ls -t ~/Backups/fur-erp/fur_erp_*.sql.gz | head -3          # выберите нужную копию
docker exec fur-erp-db-1 psql -U fur_erp -d postgres -c 'CREATE DATABASE fur_erp_restore_test'
gunzip -c ~/Backups/fur-erp/fur_erp_XXXX.sql.gz | docker exec -i fur-erp-db-1 psql -U fur_erp -d fur_erp_restore_test
docker exec -it fur-erp-db-1 psql -U fur_erp -d fur_erp_restore_test      # смотрите данные запросами SELECT
docker exec fur-erp-db-1 psql -U fur_erp -d postgres -c 'DROP DATABASE fur_erp_restore_test'   # когда закончили
```

**Случай В. Вернуть всю базу целиком (всё, что внесено после копии, пропадёт).**
1. Сделайте свежую копию текущего состояния: `scripts/backup.sh` — на случай, если откат окажется ошибкой.
2. Остановите приложение (на ноутбуке закройте dev-сервер; на сервере `docker compose -f docker-compose.prod.yml stop app`).
3. Пересоздайте пустую базу и загрузите копию (ноутбук):
```bash
docker exec fur-erp-db-1 psql -U fur_erp -d postgres -c 'DROP DATABASE fur_erp'
docker exec fur-erp-db-1 psql -U fur_erp -d postgres -c 'CREATE DATABASE fur_erp'
gunzip -c ~/Backups/fur-erp/fur_erp_XXXX.sql.gz | docker exec -i fur-erp-db-1 psql -U fur_erp -d fur_erp
```
   Сервер: то же, но `docker compose -f docker-compose.prod.yml exec -T db psql …` и копии из `~/backups/fur-erp/db_*.sql.gz`.
4. Файлы (если их тоже нужно вернуть): ноутбук — `tar -xzf ~/Backups/fur-erp/uploads_XXXX.tar.gz -C uploads`; сервер — команда из `docs/DEPLOY.md`, шаг 9.
5. Запустите приложение и проверьте «Сводку» и число закупок.

Время копии указано в имени файла (`20261004_201541` = 04.10.2026 20:15:41). Проверка восстановления выполнена, результат записан в `docs/DEPLOY.md`.

## 5. Что делать, если тестировщик удалил лишнее

1. Не вносите новых правок в эту запись, сообщите время и что именно удалено.
2. Откройте «История» → найдите удаление → там снимок значений до удаления.
3. Для одной записи — внесите значения заново по снимку. Для массового удаления — случай Б (пробная база), перенесите нужное руками или случай В, если потеряно много.
4. Если нужной копии нет — запустите `scripts/backup.sh` сразу (чтобы хотя бы зафиксировать текущее) и скажите об этом владельцу.

## 6. Чего НЕ делать

- **`docker compose down -v`** — флаг `-v` удаляет тома: пропадут база и файлы. Останавливать можно только `docker compose stop` или `docker compose down` (без `-v`).
- **`docker volume rm`**, `docker volume prune`, `docker system prune --volumes` — то же самое.
- **`prisma migrate reset`** и `prisma db push --force-reset` — стирают всю базу и создают заново.
- Не запускайте скрипты из `scripts/` на боевой базе без копии (`scripts/backup.sh`) — многие из них массово правят данные.
- Не открывайте пробные записи на боевой базе: проверяйте «на пробу» в копии (случай Б) или на своих тестовых записях, которые потом удаляете.
- Не удаляйте папку `uploads/` и не меняйте имя папки проекта на сервере (`fur-erp` входит в имя тома).
- Не храните единственную копию на том же диске: раз в неделю копируйте `~/Backups/fur-erp` (или `~/backups/fur-erp` с сервера) в другое место.

## 7. Перед обновлением версии

1. `sh deploy/backup.sh` (сервер) / `scripts/backup.sh` (ноутбук).
2. `sh scripts/check-migration-safety.sh` — если пишет «ОПАСНО», сначала прочитайте миграцию.
3. Обновление: `git pull && docker compose -f docker-compose.prod.yml up -d --build`.
4. Проверьте «Сводку»; если что-то не так — случай В.
