# Публикация «THE FUR» для внешних тестировщиков

Версия документа: 15.10.2026. Приложение и стенд подготовлены к публикации в интернет, **но сами ничего не публикуют**: хостинг, адрес и момент выдачи ссылки выбираете вы.

## Главное правило: внешним — только обезличенная демо-база

На публичный адрес **никогда не выкладывается ваша рабочая база и ваши документы**. Внешние тестировщики видят отдельную демо-базу `fur_erp_demo`: названия контрагентов вымышленные, деньги умножены на скрытый коэффициент, переписка, журнал изменений, заметки и файлы удалены (что именно маскируется — в разделе «Демо-база» ниже). Рабочая база остаётся на вашем ноутбуке.

Защита в четыре слоя (каждый работает независимо от остальных):
1. **Общий замок сайта** (логин/пароль в окне браузера, настраивает Caddy) — без него страница входа даже не открывается.
2. **Вход в приложение** по личному логину и паролю тестировщика: защита от перебора, журнал входов, срок сессии 7 дней.
3. **Роли и изоляция**: поставщик видит только своё; чужие записи по прямой ссылке дают «не найдено» (проверено автоматически: `scripts/test-security.ts`).
4. **Данные демонстрационные**: даже при худшем сценарии утекают вымышленные данные.

## Что нужно знать про переключатели

Задаются в файле `.env` на сервере. Для публичного стенда **все три должны быть `false`** (так и записано по умолчанию):

| Переменная | Что делает | Для внешних |
|---|---|---|
| `ALLOW_REGISTRATION` | любой посетитель может зарегистрировать свою компанию | `false` |
| `ALLOW_DEMO_LOGIN` | пароли демо-пользователей показываются прямо на странице входа | `false` |
| `ALLOW_ROLE_SWITCH` | у владельца появляется кнопка «Сменить на кабинет поставщика» (показ вами самим себе) | `false` |

В боевом режиме (`NODE_ENV=production`) без явного `true` эти возможности выключены, даже если переменную забыли. Сервер вообще не запустится, если не задан `AUTH_SECRET` или он слишком простой (меньше 32 знаков).

Остальные переменные: `DOMAIN` (адрес сайта), `DB_PASSWORD`, `AUTH_SECRET`, `BASIC_USER`/`BASIC_HASH` (общий замок), `COMPOSE_PROFILES` (`server` или `tunnel`), `DEMO_BUILD` (`true` — демо-сборка без вшитых реальных справочников), `TELEGRAM_*` (по желанию). Образец: `deploy/.env.prod.example`. Адреса приложения (`AUTH_URL`, `NEXTAUTH_URL`) и `UPLOAD_DIR=/app/uploads` compose задаёт сам.

# Часть 1. Подготовить демо-базу (на вашем ноутбуке, один раз и после каждого заметного обновления данных)

Нужен запущенный Docker с контейнером `fur-erp-db-1` (как обычно при работе).

1. Откройте программу «Терминал» и перейдите в папку проекта:
   ```bash
   cd /Users/petr/Projects/fur-erp
   ```
2. Остановите приложение, если оно собиралось (`next build` не должен идти параллельно). Рабочую базу **не трогаем**: скрипт сам делает её копию.
3. Сделайте свежую копию рабочей базы под именем `fur_erp_demosrc` (источник для обезличивания):
   ```bash
   docker exec fur-erp-db-1 psql -U fur_erp -d postgres -c "drop database if exists fur_erp_demosrc" -c "create database fur_erp_demosrc"
   docker exec fur-erp-db-1 pg_dump -U fur_erp fur_erp | docker exec -i fur-erp-db-1 psql -U fur_erp -d fur_erp_demosrc -q
   ```
4. Запустите обезличивание:
   ```bash
   sh scripts/make-demo-db.sh fur_erp_demosrc
   ```
   Через 1–2 минуты в конце должно быть написано «Контроль: прежние названия, почты и имена в базе не найдены.» и «Готово».
5. Результат:
   - демо-база `fur_erp_demo` в вашем локальном контейнере (для проверки);
   - дамп для переноса на хостинг: `~/Backups/fur-erp/demo/fur_erp_demo_<дата>.sql.gz` и заглушки документов `demo_uploads_<дата>.tgz` (права 600);
   - **логины и пароли демо-пользователей: `~/Backups/fur-erp/demo-logins.txt`** (права 600; открыть: `open -e ~/Backups/fur-erp/demo-logins.txt`). Пароли случайные, в чат их не отправляйте; тестировщику передавайте только его строку, отдельным сообщением.
6. Проверка согласованности чисел на демо-базе (в логин-файле есть служебная строка «коэффициент денег N» — подставьте N):
   ```bash
   DATABASE_URL="postgresql://…/fur_erp_demo" RECON_TOL_SCALE=N node --conditions=react-server node_modules/.bin/tsx scripts/test-reconciliation.ts
   ```
   Должно быть «расхождений 0» (при пробном прогоне: 495 проверок, 0 расхождений).
7. Удалите промежуточную копию: `docker exec fur-erp-db-1 psql -U fur_erp -d postgres -c "drop database fur_erp_demosrc"`.

Демо-пользователи: **Демо Владелец** (OWNER), **Демо Технолог**, **Демо Закупщик**, **Демо Бухгалтер**, **Веллмех-демо (кабинет)** (SUPPLIER).

## Что маскируется, а что нет
Маскируется: названия, ИНН, адреса, телефоны и почты контрагентов (Веллмех → «Веллмех-демо», остальные — «Поставщик №N»/«Заказчик №N»); **все денежные суммы умножаются на один целый коэффициент 3–9** (оплаты, цены, стоимости, суммы счетов, расчёты лотов) — поэтому суммы и сверки внутри базы сходятся, а реальные цифры не видны; заметки, примечания, комментарии, решения владельца, чаты, письма, журнал изменений; имена «кто подтвердил/принял»; номера договоров; ссылки на Google Drive и имена файлов (все документы указывают на одну заглушку PDF); вложения чата, фото примерок, входящие поставщика; пользователи и пароли. Из старых названий в базе ничего не остаётся (скрипт сам проверяет все текстовые поля).

Не маскируется (осознанно): даты, количества, названия видов меха, материалов и аукционов, названия изделий и артикулы, номера закупок/ТЗ/лотов/счетов/п-п (нужны для связей), пропорции цен (коэффициент один). В тексте интерфейса (подписях экранов) слово «Веллмех» встречается — это название кабинета, а не данные.

# Вариант 1. Сервер Timeweb Cloud + Docker (работает круглосуточно)

Ориентир: 1,5–3 часа в первый раз. Стоимость — месячная плата за сервер (тарифы смотрите на timeweb.cloud; для теста хватает 2 ядра, 4 ГБ памяти, 50 ГБ диска). Всё нужное есть в репозитории: `Dockerfile`, `docker-compose.prod.yml`, `deploy/Caddyfile`, `deploy/setup-env.sh`, `deploy/update.sh`, `deploy/backup.sh`.

Почему VPS, а не «Приложения» Timeweb и не управляемая база: приложение хранит загруженные документы на диске сервера (на платформенных «Приложениях» диск обычно временный), а база в том же Docker проще и дешевле.

## Что понадобится заранее
1. Аккаунт на https://timeweb.cloud (регистрацию и оплату делаете вы сами).
2. Компьютер с «Терминалом» (macOS).
3. Доступ к репозиторию GitHub `PetrFedin/fur-erp` (приватный: сервер читает его по ключу, шаг 6) **или** способ перенести код архивом (см. ниже «Без GitHub»).
4. Демо-база из части 1.
5. (Необязательно) своё доменное имя. Без домена используем адрес вида `185-12-34-56.sslip.io` — бесплатно, HTTPS работает.

## Шаг 1. Заказать сервер
1. Панель Timeweb Cloud → «Облачные серверы» → «Создать сервер».
2. Образ: **Ubuntu 24.04** (если в маркетплейсе есть образ с Docker — можно его, тогда шаг 4 пропустите).
3. Конфигурация: 2 vCPU, 4 ГБ RAM, диск 50 ГБ NVMe. Регион: Москва или Санкт-Петербург.
4. Доступ: **SSH-ключ**. Нет ключа — в Терминале на ноутбуке:
   ```bash
   ssh-keygen -t ed25519 -C "fur-erp-server"
   cat ~/.ssh/id_ed25519.pub
   ```
   Скопируйте напечатанную строку и вставьте в Timeweb как новый SSH-ключ. Вход по паролю не включайте.
5. Нажмите «Создать». Через 1–3 минуты появится **IP-адрес** (например `185.12.34.56`) — запишите.

## Шаг 2. Подключиться к серверу
```bash
ssh root@185.12.34.56
```
(вместо IP — ваш). На вопрос «Are you sure…» ответьте `yes`.

## Шаг 3. Базовая защита (файрвол)
```bash
apt update && apt upgrade -y
apt install -y ufw
ufw default deny incoming
ufw default allow outgoing
ufw limit 22/tcp
ufw allow 80/tcp
ufw allow 443/tcp
ufw --force enable
ufw status
```
Открыты только вход по SSH (с ограничением частоты попыток) и сайт (80/443). Порт базы данных наружу не открывается — в `docker-compose.prod.yml` его нет, и так должно оставаться. Дополнительно в панели Timeweb можно включить «Сетевой экран/фаервол» с теми же правилами.

## Шаг 4. Установить Docker
```bash
curl -fsSL https://get.docker.com | sh
docker --version
docker compose version
```
Должны напечататься версии обеих команд.

## Шаг 5. Выбрать адрес сайта
- **Без домена:** IP `185.12.34.56` → адрес `185-12-34-56.sslip.io` (точки заменить дефисами).
- **Свой домен:** в DNS-панели домена добавьте запись типа **A**: имя `erp` (получится `erp.вашдомен.ru`) → значение `185.12.34.56`. Через 5–30 минут `ping erp.вашдомен.ru` должен отвечать ваш IP.

## Шаг 6. Скачать проект на сервер
Репозиторий приватный: сервер получает «ключ только на чтение».
1. На сервере: `ssh-keygen -t ed25519 -f ~/.ssh/deploy_key -N ""` затем `cat ~/.ssh/deploy_key.pub`.
2. На GitHub: репозиторий `PetrFedin/fur-erp` → Settings → Deploy keys → Add deploy key → вставьте строку, название `timeweb`, **галочку «Allow write access» НЕ ставьте** → Add key.
3. На сервере:
   ```bash
   cat >> ~/.ssh/config <<'CFG'
   Host github.com
     IdentityFile ~/.ssh/deploy_key
     StrictHostKeyChecking accept-new
   CFG
   cd ~ && git clone git@github.com:PetrFedin/fur-erp.git fur-erp
   cd fur-erp && git log --oneline | head -3
   ```
   Папка обязательно называется `fur-erp` (от этого зависит имя тома в скриптах копий).

**Без GitHub:** на ноутбуке `cd /Users/petr/Projects/fur-erp && git archive --format=tar.gz -o /tmp/fur-erp-src.tgz HEAD && scp /tmp/fur-erp-src.tgz root@185.12.34.56:/root/`, на сервере `mkdir -p ~/fur-erp && tar xzf ~/fur-erp-src.tgz -C ~/fur-erp`. Обновлять тогда придётся повторной отправкой архива.

## Шаг 7. Создать секреты (.env) — одной командой
```bash
cd ~/fur-erp
sh deploy/setup-env.sh
```
Скрипт спросит адрес сайта (из шага 5) и логин общего замка (например `tester`), сам сгенерирует пароль базы, секрет входа и **пароль общего замка**. Пароль замка показывается **один раз** — запишите его (в менеджер паролей или блокнот). Файл `.env` создаётся с правами 600; никому его не пересылайте.

Затем включите демо-сборку (без вшитых реальных справочников):
```bash
sed -i 's/^DEMO_BUILD=.*/DEMO_BUILD=true/' .env
grep -E '^(ALLOW_|DEMO_BUILD|COMPOSE_PROFILES)' .env
```
Должно быть: три `ALLOW_… =false`, `DEMO_BUILD=true`, `COMPOSE_PROFILES=server`.

## Шаг 8. Перенести демо-базу с ноутбука
Это делается на **ноутбуке**:
```bash
cd ~/Backups/fur-erp/demo
ls -t fur_erp_demo_*.sql.gz | head -1     # самый свежий дамп
ls -t demo_uploads_*.tgz | head -1        # заглушки документов
scp "$(ls -t fur_erp_demo_*.sql.gz | head -1)" root@185.12.34.56:/root/fur_erp.sql.gz
scp "$(ls -t demo_uploads_*.tgz | head -1)" root@185.12.34.56:/root/uploads.tgz
```
**Не переносите** дамп рабочей базы `fur_erp` и папку `uploads` ноутбука.

## Шаг 9. Первый запуск и загрузка данных (на сервере)
```bash
cd ~/fur-erp
docker compose -f docker-compose.prod.yml up -d db
sleep 15
gunzip -c ~/fur_erp.sql.gz | docker compose -f docker-compose.prod.yml exec -T db psql -U fur_erp -d fur_erp -v ON_ERROR_STOP=1
docker compose -f docker-compose.prod.yml up -d --build
```
Первая сборка занимает 5–10 минут (внутри: `prisma generate` → `next build`). При старте приложение само применяет миграции базы (`prisma migrate deploy`, сейчас 58 миграций; дамп уже содержит их — повторно ничего не применится). Затем заглушки документов:
```bash
docker run --rm -v fur-erp_fur_erp_uploads:/data -v /root:/in alpine sh -c "cd /data && tar xzf /in/uploads.tgz"
docker compose -f docker-compose.prod.yml restart app
```
Проверка: `docker compose -f docker-compose.prod.yml ps` — три сервиса (`db`, `app`, `caddy`) в статусе Up. Логи: `docker compose -f docker-compose.prod.yml logs -f app` (выход `Ctrl+C`). Если приложение сразу падает с сообщением «Небезопасные настройки окружения» — прочитайте, чего не хватает (секрет входа не задан или слишком короткий).

(Шаги 2–9 для чистого сервера можно заменить одним скриптом `deploy/temp-server.sh` — см. заголовок файла; он ожидает файлы `fur-erp-src.tgz`, `fur_erp.sql.gz`, `uploads.tgz` в `/root`.)

## Шаг 10. Проверить сайт (по чек-листу ниже)
1. Откройте `https://<ваш адрес>` — браузер спросит логин и пароль общего замка; без них ничего не открывается. Замок в адресной строке — HTTPS работает (сертификат Caddy получает сам в течение минуты).
2. После замка — страница входа в приложение: **на ней не должно быть демо-паролей и ссылки «Зарегистрировать компанию»**. Адрес `/register` перекидывает на вход.
3. Войдите «Демо Владельцем» (пароль в `~/Backups/fur-erp/demo-logins.txt`) — откройте Главную, «Сырьё», закупку, ТЗ: имена вымышленные, цифры не совпадают с реальными.
4. Войдите «Веллмех-демо» — виден только кабинет поставщика.

## Шаг 11. Выдать доступ тестировщику
1. Войдите «Демо Владельцем» → Настройки → Пользователи → добавьте сотрудника тестировщика: email, имя, **роль** («Наблюдатель» — только просмотр; нужные рабочие роли — по задаче), пароль не короче 10 знаков (лучше случайный).
2. Передайте: адрес сайта; логин и пароль общего замка; личный логин и пароль входа — **тремя разными сообщениями/каналами**; файл `docs/TESTING.md`.
3. Когда тест окончен — удалите или деактивируйте пользователей (Настройки → Пользователи) и смените пароль общего замка (см. «Поменять пароль замка»).

## Шаг 12. Резервные копии
Даже у демо-стенда есть ваши настройки тестирования. Один раз:
```bash
cd ~/fur-erp
sh deploy/backup.sh          # проверка: в ~/backups/fur-erp появились db_*.sql.gz и uploads_*.tgz
crontab -e
```
Добавьте строку (каждую ночь в 03:30):
```
30 3 * * * cd /root/fur-erp && sh deploy/backup.sh >> /root/backup.log 2>&1
```
Хранятся 14 последних копий. Раз в неделю скачивайте их на ноутбук: `scp -r root@185.12.34.56:/root/backups/fur-erp ~/Backups/fur-erp-server`. В Timeweb можно включить автоматические бэкапы всего диска (платная опция). **Проверьте восстановление хотя бы раз:** `gunzip -c файл | docker exec -i fur-erp-db-1 psql -U fur_erp -d <пустая_база>` (на ноутбуке) — копия, которую не пробовали восстановить, не копия.

## Мониторинг
- Состояние: `curl -s https://<адрес>/api/health` (через общий замок: `curl -u логин:пароль …`) → `{"ok":true,…}`. Подробная готовность (только для владельца): `/api/ready?details=1` после входа.
- Бесплатный внешний монитор доступности (по желанию): укажите ему `https://<адрес>/api/health` с логином замка в настройках проверки.
- Логи: `docker compose -f docker-compose.prod.yml logs --tail=200 app` (входы и неудачные попытки пишутся строкой `[auth]`); `... logs caddy`.
- Диск: `df -h` (раз в неделю; если занято больше 80% — удалить старые копии в `~/backups`).
- Журнал входов в самом приложении: «История» → записи «Вход», «Неудачная попытка входа», «Вход заблокирован» (после 10 неверных паролей подряд вход блокируется на 10 минут).

## Обновление до новой версии
На сервере одной командой:
```bash
cd ~/fur-erp && sh deploy/update.sh
```
Порядок внутри: **1) резервная копия → 2) `git pull` → 3) сборка образа (`prisma generate` → `next build`) → 4) запуск (`prisma migrate deploy` применяет миграции автоматически) → 5) проверка здоровья**. Если проверка не прошла, скрипт покажет, куда смотреть; откат — вернуть прежний коммит и восстановить базу из копии шага 1.
Вручную то же самое: `sh deploy/backup.sh && git pull --ff-only && docker compose -f docker-compose.prod.yml up -d --build`.

## Поменять пароль общего замка
```bash
cd ~/fur-erp
docker run --rm caddy:2-alpine caddy hash-password --plaintext 'НОВЫЙ_ПАРОЛЬ'
nano .env      # заменить значение BASIC_HASH (в одинарных кавычках!) и при желании BASIC_USER
docker compose -f docker-compose.prod.yml up -d caddy
```

## Убрать стенд целиком
`cd ~/fur-erp && docker compose -f docker-compose.prod.yml down -v` (удалит базу и файлы стенда) и удалить сервер в панели Timeweb.

# Вариант 2. Временный доступ с ноутбука через защищённый туннель

Для короткого теста на несколько часов или дней, пока не заказан сервер. Как это работает: на ноутбуке поднимается **отдельная копия** приложения с **демо-базой** (не вашей рабочей), перед ней — Caddy с общим замком-паролем, а сервис `cloudflared` выдаёт временный адрес `https://что-то.trycloudflare.com` без регистрации и открытия портов на роутере.

**Оговорки.**
- **Пока ноутбук выключен, спит или без интернета — ссылка не работает.** Не закрывайте крышку; можно запретить сон: `caffeinate -dimsu &` (остановить: `killall caffeinate`).
- Адрес **меняется при каждом запуске** туннеля — новую ссылку нужно отправлять заново.
- Сервис `trycloudflare` бесплатный и без гарантий доступности: для долгого теста берите вариант 1.
- Туннель — сторонний сервис: через него проходит трафик демо-стенда (HTTPS). Именно поэтому на нём **только демо-база и пароль замка**.
- Рабочее приложение на `localhost:3200` и рабочая база не затрагиваются: у демо-стенда свой проект Docker (`fur-erp-demo`) со своей базой.

## Шаги (на ноутбуке)
1. Подготовьте демо-базу (часть 1): понадобятся файлы в `~/Backups/fur-erp/demo`.
2. Папка стенда (чтобы не мешать рабочей):
   ```bash
   mkdir -p ~/fur-erp-demo && cd ~/fur-erp-demo
   git clone /Users/petr/Projects/fur-erp . 2>/dev/null || git -C /Users/petr/Projects/fur-erp archive --format=tar HEAD | tar x -C .
   ```
3. Секреты: `sh deploy/setup-env.sh tunnel` — спросит только логин замка и покажет пароль замка **один раз** (запишите). Затем: `sed -i '' 's/^DEMO_BUILD=.*/DEMO_BUILD=true/' .env`.
4. Запустите базу и загрузите демо-дамп:
   ```bash
   COMPOSE_PROFILES=tunnel docker compose -p fur-erp-demo -f docker-compose.prod.yml -f docker-compose.tunnel.yml up -d db
   sleep 15
   gunzip -c "$(ls -t ~/Backups/fur-erp/demo/fur_erp_demo_*.sql.gz | head -1)" | docker compose -p fur-erp-demo -f docker-compose.prod.yml -f docker-compose.tunnel.yml exec -T db psql -U fur_erp -d fur_erp -v ON_ERROR_STOP=1
   ```
5. Запустите всё (первая сборка — 5–10 минут):
   ```bash
   COMPOSE_PROFILES=tunnel docker compose -p fur-erp-demo -f docker-compose.prod.yml -f docker-compose.tunnel.yml up -d --build
   docker run --rm -v fur-erp-demo_fur_erp_uploads:/data -v "$HOME/Backups/fur-erp/demo":/in alpine sh -c "cd /data && tar xzf /in/$(ls -t $HOME/Backups/fur-erp/demo/demo_uploads_*.tgz | head -1 | xargs basename)"
   ```
6. Узнайте адрес:
   ```bash
   docker compose -p fur-erp-demo -f docker-compose.prod.yml -f docker-compose.tunnel.yml logs cloudflared | grep -o 'https://[a-z0-9-]*\.trycloudflare\.com' | tail -1
   ```
7. Откройте адрес сами (по чек-листу ниже), затем отправьте тестировщику: адрес, логин/пароль замка и личный логин/пароль — отдельными сообщениями.
8. Остановить доступ немедленно: `docker compose -p fur-erp-demo -f docker-compose.prod.yml -f docker-compose.tunnel.yml down` (добавьте `-v`, чтобы удалить и демо-базу).

# Чек-лист безопасности «перед выдачей ссылки»

Отметьте каждый пункт сами:
- [ ] Стенд работает на **демо-базе** (в «Демо Владелец» имена вымышленные; нет вашего ТЗ/реальных контрагентов). Рабочая база и папка `uploads` ноутбука на сервер **не** копировались.
- [ ] В `.env`: `ALLOW_REGISTRATION=false`, `ALLOW_DEMO_LOGIN=false`, `ALLOW_ROLE_SWITCH=false`, `DEMO_BUILD=true`; `AUTH_SECRET` сгенерирован скриптом (не придуман вручную).
- [ ] Сайт открывается только по `https://` (замок в адресной строке), а `http://` перекидывает на https.
- [ ] Без общего замка страницы не открываются; с замком — на странице входа **нет демо-паролей** и **нет ссылки «Зарегистрировать компанию»**; `/register` перекидывает на вход.
- [ ] Порты наружу: только 22 (SSH с лимитом), 80, 443 (`ufw status`); база наружу не открыта (`docker compose … ps` — у `db` нет `0.0.0.0:…`).
- [ ] На сервере вход по SSH только по ключу; пароль root не используется.
- [ ] Старые тестовые пользователи (например `anna@qa-test.ru`) на стенде отсутствуют — в демо-базе их нет, проверьте в «Настройки → Пользователи».
- [ ] Тестировщику выданы личные логины с минимальной ролью («Наблюдатель» или нужная рабочая), а не «Демо Владелец».
- [ ] Логин/пароль замка и личные пароли переданы **разными сообщениями**; файл `demo-logins.txt` никому не пересылался.
- [ ] Настроены ночные резервные копии (`crontab -l`) и один раз проверено восстановление.
- [ ] Известно, как быстро выключить стенд (`down` / удалить сервер) и сменить пароль замка.
- [ ] После теста: пользователи тестировщиков удалены, пароль замка сменён или стенд остановлен.

Ожидается «ВСЕ ПРОВЕРКИ ПРОЙДЕНЫ». Скрипт откажется работать на базе, имя которой не оканчивается на `_sec`, `_demo` или `_test`.

# Что защищено в приложении (кратко для владельца)

- **Вход:** пароли хранятся хэшем bcrypt (cost 12), пароль при создании пользователя — не короче 10 знаков и не из «простых»; после 10 неверных попыток (почта+адрес) вход блокируется на 10 минут, ещё два общих замка на перебор многих почт с одного адреса и одной почты с многих адресов; прямой запрос к `/api/auth` тоже считается; одинаковый ответ и время на неверную почту и неверный пароль; все входы, неудачи и блокировки пишутся в журнал.
- **Сессия:** cookie `HttpOnly`, `Secure`, `SameSite=Lax`; живёт 7 дней; роль и активность пользователя перечитываются из базы при каждом запросе (удалили/деактивировали — доступ пропал сразу).
- **Доступ:** каждая страница, API и серверное действие проверяют вход, организацию и роль; поставщик — «по умолчанию закрыто», видит только свои отгрузки/расчёты/файлы; файлы отдаются только после проверки прав, с `nosniff` и `Cache-Control: private`.
- **Загрузки:** тип проверяется по содержимому, размер ≤ 25 МБ, не более 10 файлов; xlsx/docx проверяются на «архив-бомбу» до распаковки; тело запроса ограничено (Caddy 30 МБ, приложение 26 МБ).
- **Браузер:** заголовки CSP (только свой домен), HSTS, запрет встраивания в чужие сайты, `nosniff`, Referrer-Policy, Permissions-Policy; страницы с данными не кэшируются; `X-Powered-By` отключён.
- **Формулы расчётов:** собственный разбор без `eval`; длина, число элементов и глубина вложенности ограничены.
- **Зависимости:** Next.js обновлён до 16.4.1; `npm audit --omit=dev` без критичных (остаток — см. отчёт: два пункта инструментов сборки и exceljs/uuid, не вызываемые из пользовательского ввода).

## Остаточные риски (решение за вами)
1. **Общий замок Caddy без лимита попыток** — подбор возможен, поэтому пароль замка должен быть случайным и длинным (скрипт даёт 20 знаков). При подозрении — сменить пароль замка.
2. **Внутренний счётчик попыток входа хранится в памяти приложения**: после перезапуска сбрасывается (общий замок и длинные пароли это компенсируют).
3. **Роли внутри организации** («Закупщик», «Бухгалтер» и т. д.) видят данные организации в пределах своей роли; тестировщику выдавайте минимальную роль.
4. **Туннель с ноутбука** (вариант 2) — сторонний транзит трафика и зависимость от включённого ноутбука; допустим только с демо-базой.
5. **Telegram-мост** на стенде для внешних лучше не включать (оставить `TELEGRAM_*` пустыми).
6. **Образ Docker** в этой среде разработки не удалось собрать из-за сети (не проходит проверка сертификата при загрузке бинарников Prisma и шрифтов); на сервере Timeweb сборка идёт по обычной схеме. Состав контекста сборки проверен: `.env`, `docs-inventory`, `uploads`, `.claude`, `*.txt`, `Backups` в образ не попадают (`.dockerignore`).
7. Реальные подписи «Веллмех» в тексте интерфейса (названия экранов) остаются; данные — нет.

## Чат с поставщиком и Telegram (по желанию)

Чат (`/chat`) работает сразу, ничего настраивать не нужно. Чтобы сообщения дублировались в Telegram и ответы оттуда возвращались в платформу:

1. В Telegram откройте **@BotFather** → `/newbot` → придумайте имя и логин бота (логин оканчивается на `bot`). BotFather пришлёт **токен** — длинную строку вида `123456:ABC...`. Никому её не показывайте.
2. В файле `.env` на сервере добавьте строку `TELEGRAM_BOT_TOKEN="ваш_токен"` (и убедитесь, что `NEXTAUTH_URL` — настоящий адрес платформы: он попадает в ссылку «Открыть в платформе»). Токен нигде, кроме `.env`, не хранится.
3. Запустите мост: `npm run telegram` (постоянно, рядом с приложением — например, отдельным процессом/службой). Он опрашивает Telegram (long polling), сохраняет, что уже получено (`uploads/telegram-offset.json`), и дорассылает сообщения, которые не ушли сразу. Без токена он сразу завершается с понятным сообщением.
   - Вместо опроса на сервере с публичным HTTPS можно включить вебхук: задайте `TELEGRAM_WEBHOOK_SECRET` и один раз вызовите `setWebhook` с адресом `https://ВАШ-АДРЕС/api/channels/telegram/webhook` и `secret_token` того же значения.
4. Привязка людей: в платформе откройте «Чат» → «Подключить Telegram» → «Получить код»; в Telegram напишите боту `/start КОД` (код живёт 15 минут, подходит один раз).
5. Привязка групп (владелец/админ): «Настройки → Каналы» → «Получить код группы» (группа поставщика или наша внутренняя) → добавьте бота в группу Telegram и напишите там `/bind КОД`.
6. Из Telegram: просто текст — в последнее ваше обсуждение; «reply» на сообщение бота — именно в его обсуждение; `/t НОМЕР текст` — в обсуждение с номером (#N виден в заголовке сообщения и в списке чата); `/new тема` — новый запрос. Фото и документы (PDF, XLSX, DOCX, JPEG, PNG до 25 МБ) сохраняются как вложения.
7. Проверка без настоящего бота: `npx tsx scripts/telegram-stub.ts` (локальная заглушка Bot API) и в `.env` `TELEGRAM_API_BASE=http://127.0.0.1:3299`, `TELEGRAM_BOT_TOKEN=test`.

**WhatsApp** пока не подключён: в платформе есть интерфейс канала и пустой адаптер. Для реального подключения нужны аккаунт Meta Business (WhatsApp Business Platform), номер телефона и публичный HTTPS-адрес платформы для вебхука.

## Обновление версии (после новых правок)
На ноутбуке: `git push` (как сейчас). На сервере:
```bash
cd ~/fur-erp && git pull && docker compose -f docker-compose.prod.yml up -d --build
```
Миграции базы применяются автоматически при старте приложения (в `docker-entrypoint.sh`).

**Правило: перед каждым обновлением версии — `sh deploy/backup.sh`** (копия базы и файлов за минуту; без неё откатиться некуда). Затем проверьте, нет ли в новых миграциях разрушающих операций:
```bash
sh scripts/check-migration-safety.sh      # «ОПАСНО: требуется бэкап и ручная проверка» — прочитайте указанную миграцию до `up -d --build`
```
После успешного обновления поставьте новую отметку: `ls prisma/migrations | tail -1 | cut -c1-14 > scripts/.migration-baseline`. Подробности про сохранность данных и восстановление: `docs/DATA-SAFETY.md`.

## Если что-то не работает
| Симптом | Что делать |
|---|---|
| Сайт не открывается | `docker compose -f docker-compose.prod.yml ps`; `… logs caddy` (проблемы сертификата/домена), проверить DNS и что порты 80/443 открыты (`ufw status`) |
| Бесконечный вход / «Configuration» | Проверьте в `.env` `DOMAIN` и `AUTH_SECRET`; после правки `.env`: `docker compose -f docker-compose.prod.yml up -d` |
| 500 после обновления | `docker compose -f docker-compose.prod.yml logs --tail=100 app` |
| Не грузятся документы | Файлы в томе не восстановлены (шаг 9, вторая часть) или файл больше 25 МБ |
| Закончилось место | `df -h`, `docker system prune -af` (не трогает тома), удалить старые копии в `~/backups` |

## Что не входит в эту инструкцию (на будущее)
- Письма и уведомления (в приложении их нет).
- Мониторинг доступности (бесплатно: uptimerobot.com — проверка адреса сайта каждые 5 минут).
- Ограничение числа попыток входа в самом приложении (сейчас — только дополнительный пароль Caddy из шага 11.4).
- Раздельные стенды «тест» и «боевой» (когда заказчик начнёт вести реальный учёт — поднимите второй сервер или второй набор контейнеров).

## Что хранится и безопасно ли
- На сервере — реальные финансовые данные закупок и производства. Сервер в РФ (Timeweb), доступ только по SSH-ключу, база не торчит в интернет, HTTPS обязателен.
- Для теста можно заменить реальные суммы обезличенными копиями — если нужно, это отдельная задача.
