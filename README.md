# МехУчёт (fur-erp)

Мультитенантное веб-приложение для учёта закупок сырья, остатков, производства
и себестоимости. Каждая компания-клиент (Organization) видит только свои
данные; пользователи внутри компании имеют роли (владелец, администратор,
закупщик, кладовщик, технолог, бухгалтер, наблюдатель).

## Стек

- Next.js 16 (App Router, TypeScript) + Tailwind CSS
- PostgreSQL + Prisma ORM
- Auth.js (next-auth v5), учётные данные по email/паролю, JWT-сессии
- Recharts для дашборда

## Массовое заведение данных

Реальные закупки/ТЗ пользователя — это не 1-2 позиции, а обычно 10-160+ строк
за раз (см. импортированный реестр). Заполнять их по одной через форму
неудобно, поэтому на двух самых «многострочных» экранах, помимо обычной
формы на одну позицию, есть вставка сразу нескольким строками — как
скопировать из Excel и вставить:

- **Закупка → «Позиции сырья»**: вставить строки `Материал [Tab] Кол-во
  [Tab] Цена без НДС [Tab] НДС% [Tab] Лот [Tab] Сорт [Tab] Цвет` (последние
  три необязательны). Сырьё ищется по точному названию (без учёта
  регистра); не найденное — заводится автоматически как новое `RawMaterial`
  (единица измерения по умолчанию — «шт.», поправить потом на странице
  сырья).
- **ТЗ → «Списание сырья в производство»**: вставить строки `Лот [Tab]
  Количество` — лот ищется по номеру на складе сырья этого заказа. Строки,
  которые не удалось разобрать (лот не найден, не хватает остатка,
  нечисловое количество) — не пропадают молча, а перечисляются под формой,
  остальные всё равно применяются.

**Исправление уже введённых позиций закупки.** Каждая строка на странице
закупки («Позиции сырья (мех)» и «Подкладка») теперь можно открыть кнопкой
«Изменить» и поправить ошибку, не удаляя и не заводя строку заново — это
основной сценарий после вставки 10-160 строк из Excel. Правило безопасности:
пока закупка не оприходована, редактируется всё (сырьё, количество, цена,
НДС, лот, сорт, цвет). После оприходования по позиции уже создана партия
сырья (`RawMaterialLot`) — лот/сорт/цвет остаются редактируемыми всегда, а
количество/цену/НДС можно менять только пока из этой партии ничего не
списано в производство; как только `quantityRemaining` партии стало меньше
`quantityReceived`, форма блокирует эти поля с явным сообщением, сколько
единиц уже использовано. Это осознанно проще, чем пересчитывать себестоимость
задним числом по уже сделанным списаниям (`ProductionMaterialUsage`) — лот
хранит фиксированную себестоимость на весь срок жизни, и трогать её после
того, как она уже применена к производству, небезопасно.

**Исправление шапки закупки.** Раньше после создания закупки менять можно
было только курс валюты (отдельная узкая форма `updatePurchaseExchangeRate`)
— поставщик, склад, аукцион/сессия, дата заказа, валюта, № счёта и УПД были
доступны только на моменте создания. Теперь на карточке закупки кнопка
«Изменить» рядом со статусом открывает те же поля для правки
(`updatePurchase`). Правило то же, что и у позиций: доступно только пока
закупка не оприходована и не отменена — после оприходования себестоимость
каждой партии (`RawMaterialLot`) уже зафиксирована по курсу/валюте закупки
на момент приёмки (см. `receivePurchase`), и смена поставщика/склада/валюты
задним числом молча разошлась бы с уже посчитанными партиями. Смена валюты
сбрасывает курс на 1 — старый курс, введённый для другой валюты, не имеет
смысла и должен быть введён заново в блоке курса перед оприходованием.

**Исправление уже введённых списаний и расходов ТЗ.** Тот же пробел был и
на карточке заказа: списание сырья (`addMaterialUsage`) и производственный
расход (`addProductionExpense`) можно было только удалить и завести заново,
хотя `removeMaterialUsage` уже аккуратно откатывает списание на лот. Теперь
у каждой строки списания (мех и подкладка) и расхода есть кнопка
«Изменить». Для расхода это простая правка статьи/суммы/описания. Для
списания сырья правка лота/количества устроена как возврат старого
количества на прежний лот и списание нового количества с выбранного —
буквально то же самое, что удаление и повторное добавление, только одной
операцией и без потери строки в истории; проверка `quantityRemaining`
лота при этом естественным образом учитывает уже освобождённый остаток, так
что нельзя списать больше, чем реально доступно. В отличие от позиции
закупки, здесь **нет блокировки по статусу заказа**: правка разрешена и на
`COMPLETED` ТЗ безусловно — `syncCompletedOrderCost` уже умеет пересчитывать
себестоимость и остаток `FinishedGoodsStock` после любой правки списаний/
расходов (см. предыдущий пункт), так что дополнительная блокировка была бы
искусственным ограничением, а не мерой безопасности.

**Исправление шапки ТЗ (модель, размеры, даты, заказчик и т.п.).**
`createProductionOrder` заводил модель, склады, плановое количество, цвет,
размер, описание материала/подкладки, даты, заказчика, № договора/ТЗ и
цену работ только один раз — опечатку в любом из этих полей было можно
исправить только прямой правкой в БД. Теперь на карточке заказа кнопка
«Изменить» под шапкой открывает те же поля (`updateProductionOrder`).
Свободно редактируется всё описательное: цвет, размер, материал,
подкладка, даты, заказчик, № договора/ТЗ, цена работ для заказчика,
заметки — без блокировки по статусу, включая `COMPLETED`. Два поля
защищены явно, по той же логике, что и у позиции закупки
(`updatePurchaseItem`, локальный склад сырья закупки): модель изделия
нельзя сменить, если по заказу уже есть списание сырья или зафиксирован
выпуск — `materialDescription`/`lining` описывают именно эту модель, а
кнопка «Списать по норме» тянет BOM текущей модели, так что смена модели
задним числом молча разошлась бы с уже сделанными списаниями; плановое
количество нельзя уменьшить ниже уже произведённого — нельзя запланировать
меньше, чем реально выпущено. Склады сырья/готовой продукции
редактируются свободно: списания сами хранят свой склад через лот, а
остаток готовой продукции на складе фиксируется на момент завершения
заказа, так что правка склада в шапке задним числом ничего не рассинхронит.

**Убраны выдуманные названия, которых нет в источниках** (по просьбе
пользователя). Организация называлась «ООО Смоук-тест» (заглушка с самого
начала) — переименована в «MVST», как компания называется в заголовке

нет ни номера, ни второго склада), переименован в просто «Склад». См.

## Модель данных (кратко)

`Organization` → `User` (роли) · `Supplier` → `Purchase` (валюта +
`exchangeRate`, курс вводится вручную на дату сделки) → `PurchaseItem`
(цена в валюте закупки, опциональный номер лота) + `PurchaseExpense` +
`Payment`. При оприходовании: цена позиции конвертируется в рубли по курсу
закупки, доп. расходы (всегда в рублях) распределяются на позиции
пропорционально сумме — вместе это даёт себестоимость лота.

**Партионный учёт сырья (specific identification), не средневзвешенный.**
Каждая закупленная партия — отдельный `RawMaterialLot` с фиксированной на
дату поступления себестоимостью за единицу. Производство списывает сырьё с
конкретного лота по его цене (`ProductionMaterialUsage.lotId`), а не из
общего пула — потому что цена одной шкурки в разных лотах может отличаться
в разы. «Остатки по материалу» на дашборде и странице склада — это
агрегат по лотам на лету, не отдельно поддерживаемый кэш.

**НДС по каждой позиции своя ставка.** `PurchaseItem.vatRate` и
`PurchaseExpense.vatRate` хранятся отдельно на каждой строке — ставка,
действующая на дату сделки, реально меняется (в одном и том же реестре
пользователя встречаются и 20%, и 22%). Цена/сумма вводятся без НДС, при
оприходовании НДС начисляется сверху и попадает в себестоимость лота
(`RawMaterialLot.unitCost`); `materialCostExclVat`/`materialVatAmount`
хранят разбивку just сырьевой части для детализации. Общий расчёт «сколько
реально стоит закупка» — `src/lib/purchase-totals.ts`, переиспользуется
списком закупок, карточкой закупки и дашбордом, чтобы не разъезжались.

**Архив сырья** (`/lots`, объединён с бывшей страницей «Остатки») —
сводка по материалу вверху + полная история всех лотов (не только остаток
> 0), с поиском по номеру лота/материалу/цвету/сорту и ссылками на закупку
и на производственные заказы, где лот был использован («Использовано в») —
чтобы можно было найти и «подтянуть» нужную партию при планировании ТЗ.
Закупка также хранит `auctionSession`/`invoiceNumber`/`transferDocument`
(аукцион/сессия, № счёта, УПД) — как реально оформляется закупка на
пушном аукционе.

`ProductModel` + `ProductModelMaterial` (норма расхода, BOM) →
`ProductionOrder` — карточка ТЗ, поля 1:1 с примером пользователя
(материал продукции, подкладка, опционально `Client`-заказчик, номер
договора подряда, № и дата ТЗ, стоимость работ за ед.). Списание сырья —
по конкретным лотам (с текстовым поиском по номеру/цвету/сорту, т.к. лотов
может быть много), одной кнопкой «по норме BOM», или вставкой сразу
нескольких строк «Лот [Tab] Количество» (см. «Массовое заведение» ниже) —
накапливает
`ProductionExpense`; при завершении заказа себестоимость фиксируется и
создаётся приход на склад готовой продукции (`FinishedGoodsStock`,
средневзвешенная — тут разброс себестоимости не критичен). Отдельно —
розничная цена за единицу и автоматический маркап = розничная цена /
себестоимость.

**Проверено на реальном примере ТЗ №141** пользователя (14 позиций сырья
по 2 материалам, ставка НДС 22%, поставщик «Союзпушнина», лоты 31–1386):
себестоимость сырья сошлась с оригиналом ТЗ с точностью до рубля при первой
сверке. После массового импорта всего реестра (см. ниже) эти же 14 лотов
оказались общими ещё с 4 другими производственными заказами из реестра
(лот может быть распределён на несколько ТЗ) — их себестоимость теперь
считается по цене лота из сводного реестра «остатки», а не только из этого
одного ТЗ, поэтому итоговая цифра (`П-2026-0150`, ≈7,64 млн ₽ на 2 шт.)
немного отличается от изначально сверенной вручную (была ≈8,10 млн ₽) —
разница в основном из-за подкладки, которая в реестре для этого конкретного
ТЗ не была найдена парсером (раздел реестра начиная примерно с ТЗ №88
использует другую раскладку колонок) — см. следующий раздел.

**Важный нюанс, оставленный на усмотрение пользователя:** в этой версии
производственный заказ считает маржу как «стоимость работ для заказчика
минус полная себестоимость (включая закупленное нами сырьё)» — то есть
сырьё считается нашим собственным. В реальном ТЗ раздел «Заказчик передал»
предполагает, что материал может быть давальческим (собственность
заказчика) — тогда его стоимость не должна вычитаться из выручки за
работу. Сейчас это не разделено; если нужно — можно добавить признак
«давальческое сырьё» на заказ, который исключает стоимость сырья из
расчёта маржи.

**Оплаты — отдельно по закупкам и отдельно по производству.** `Payment`
(поставщику, привязан к закупке) остался как был. Добавлен `ProductionPayment`
— отдельный учёт оплат ОТ заказчика (карточка ТЗ показывает «Стоимость
работ / Оплачено / Остаток к оплате»), не связанный с закупочными
оплатами. Одна оплата может покрывать сразу несколько ТЗ одного заказчика
— клиент часто платит одной суммой за несколько сделанных заказов, или
вносит аванс — поэтому `ProductionPayment` связан с `ProductionOrder`
через таблицу-связку `ProductionPaymentOrder` (многие-ко-многим), а не
напрямую; при добавлении оплаты на карточке ТЗ можно отметить и другие ТЗ
того же заказчика, которые она тоже покрывает. Тип оплаты — `Аванс` /
`Доплата` / `Окончательная`.

**Розничная цена — одно число на артикул, не на ТЗ.** Раньше
`ProductionOrder.retailPrice` и `ProductModel.sellingPrice` редактировались
независимо и расходились. Теперь оба поля обновляются вместе, с какой бы
страницы (карточка ТЗ или «Товар и цены») её ни поменяли: правка на любой
из двух страниц сразу проставляет цену и на модель, и на все её ТЗ, маркап
пересчитывается сам — как «ПРЦ», один параметр на артикул в исходном
экселе, а не отдельная цифра на каждую партию.

**Любое ТЗ редактируется, независимо от статуса.** Списание меха/подкладки
и производственные расходы раньше были доступны только для
`PLANNED`/`IN_PROGRESS` заказов — а после массового импорта реестра все
159 ТЗ сразу `COMPLETED`, то есть исправить ошибку ввода было физически
нельзя. Теперь форма списания, вставка из таблицы и кнопки «Отменить» /
«Удалить» показаны всегда; для завершённого заказа правка автоматически
пересчитывает `materialCost`/`expenseCost`/`totalCost`/`unitCost`
(`syncCompletedOrderCost` в `production/actions.ts`) и переносит разницу в
себестоимости на `FinishedGoodsStock` (с записью `FinishedGoodsMovement`
типа `ADJUSTMENT_IN`/`ADJUSTMENT_OUT` для аудита), чтобы остатки готовой
продукции и «Товар и цены» не расходились с фактом. Количество
фактически произведённого тоже можно поправить после завершения — отдельная
форма, которая аналогично пересчитывает себестоимость за ед. и остаток на
складе. Проверено вручную: списание/возврат позиции на завершённом ТЗ
корректно откатывает и накатывает себестоимость и остаток готовой
продукции до копейки.

**Подкладка — отдельным разделом.** И на карточке закупки, и на карточке ТЗ
позиции разделены на «мех» и «Подкладка» (по `RawMaterial.unit === "M"` —
ткань меряется в метрах, мех в штуках, разделение уже было в данных, просто
не было в интерфейсе): отдельная форма добавления, отдельная таблица.
На ТЗ выбор подкладки при списании — тот же самый пикер лота, что и для
меха, просто в своей карточке и со списком только тканевых лотов. На
`/lots` — то же самое: «Мех» и «Подкладка» теперь два полностью отдельных
блока (свой итоговый отчёт, свои остатки по складам, свой архив лотов), а
не одна общая таблица на оба типа сырья. У каждой партии подкладки —
своя цена за метр и своя ставка НДС (у мехового сырья ставка тоже может
отличаться от партии к партии) — так же, как у мехового лота, ничего
общего между тканями не усреднялось.

**Подкладка — один пул на ткань, а не лот на поступление.** Изначально
подкладка была устроена как у меха — новая партия при оприходовании закупки
всегда создавала новый `RawMaterialLot`. На практике это давало 25 отдельных
строк «Подкладочная ткань №24» в одной закупке (одна на каждый ТЗ, куда
ушла ткань), хотя ткань закупается и хранится по номерам, без разбивки на
партии. `scripts/consolidate-lining-lots.ts` объединил уже существовавшие
лоты в один агрегированный пул на ткань (сумма количеств/стоимостей,
средневзвешенная себестоимость за метр, `lotNumber` очищен — это больше не
одна конкретная партия). Чтобы это не воссоздавалось при каждой новой
закупке, `receivePurchase` теперь для позиций подкладки (`rawMaterial.unit
=== "M"`) вызывает `addOrPoolLiningLot` (`src/lib/stock.ts`) вместо
`createRawMaterialLot`: если у ткани уже есть лот — количество и стоимость
добавляются в него (средневзвешенно, не перезаписью — `unitCost` и
себестоимость без НДС/НДС пересчитываются по формуле
`(старое*старое_кол-во + новое*новое_кол-во) / итоговое_кол-во`), а новая
позиция закупки (`PurchaseItem`) просто привязывается к тому же лоту; если
лота ещё нет — создаётся первый, как раньше. Это потребовало перевернуть
связь `RawMaterialLot` ↔ `PurchaseItem`: раньше FK (`purchaseItemId`,
`@unique`) был на лоте, то есть ровно один `PurchaseItem` на лот — этого
достаточно для меха (специфическая идентификация, свой лот на каждое
поступление), но не для пула ткани, куда со временем может прийти много
позиций закупки с разных документов. Теперь FK (`lotId`, без `@unique`)
на стороне `PurchaseItem`, а у `RawMaterialLot` — список `purchaseItems[]`;
для меха на практике всё так же ровно один `PurchaseItem` на лот, просто
это больше не проверяется ограничением БД. Ручная правка количества/цены
позиции закупки (`updatePurchaseItem`) на такой объединённой позиции
блокируется отдельной проверкой (нельзя пересчитать себестоимость одной
позиции пула, не трогая вклад остальных) — доступны только лот/сорт/цвет,
как и для уже списанного лота.

**«Товар и цены»** (`/articles`) — отдельная страница со списком артикулов
(`ProductModel`), их средневзвешенной себестоимостью по завершённым ТЗ,
редактируемой розничной ценой (`ProductModel.sellingPrice`) и посчитанным
маркапом; плюс сводка сверху (кол-во артикулов, выпущено шт., стоимость по
розничным ценам). Себестоимость — ссылка на `/production?model=…`
(отфильтрованный список ТЗ этой модели), чтобы провалиться в детализацию,
из чего сложилась цифра.

**Финальный отчёт по сырью** — на `/lots` вверху и на `/dashboard` отдельным
блоком: таблица по каждому материалу (куплено всего / использовано /
остаток / стоимость остатка) с итогом по всем материалам, вместо только
разбивки по складам.

**Навигация** упрощена: «Производство» → «План поставки» → «Товар и цены» →
«Модели изделий»; «Остатки готовой продукции» и «Заказчики» убраны из меню
(страницы остались рабочими, просто без прямой ссылки — учёт по
давальческим заказчикам сейчас не в фокусе, но данные не удалены).

**«План поставки»** (`/supply-plan`, модель `SupplyPlanEntry`) — верхнеуровневая
плановая сетка: артикулы по строкам, месяцы по столбцам, независимая от
конкретных ТЗ. В каждой ячейке — одна или несколько записей (разные размеры/
партии одного артикула в одном месяце), у каждой: статус, количество,
опциональная дата события, заметка; статус редактируется инлайн. Набор
статусов (`SupplyPlanStatus`) взят из реальной таблицы отслеживания
пользователя («Копия производство на 22092026.xlsx»): Запланировано → Запуск
→ В работе у скорняка → В работе у портной → Сдано/произведено, плюс
Отменено. Это отдельный инструмент планирования, не привязанный к
списанию сырья/себестоимости конкретного `ProductionOrder` — если нужно
жёстко связать план с фактическим ТЗ (например, автоматически переводить
план в «произведено» при завершении заказа), это можно добавить отдельно.

План заполнен из реального файла пользователя (`scripts/import-supply-plan.ts`
+ `scripts/supply_plan_import.json`): там каждая строка — один экземпляр
изделия (размер) с цепочкой дат по стадиям и текстовым примечанием; статус
определён по приоритету «отменён» → «сдано» (есть дата сдачи или слово
«сдан(о/а)» в примечании) → «у портной» → «у скорняка» → «запуск» →
«запланировано», затем сгруппировано по (артикул, месяц, статус) с
подсчётом штук. 9 артикулов из этого файла (М001Е, М023, М025, М030, М039,
М040, М044, М054, М055) отсутствовали в базе — заведены как новые
`ProductModel` без BOM/себестоимости (это будущая, ещё не начатая
производством продукция).

**Путаница кириллица/латиница в кодах артикулов — устранена.** В исходном
файле реестра оказался скрытый лист «Лист16» с официальным соответствием
кириллических кодов (как их набирали в одних листах, например «МОО1К» с
кириллической «О» вместо нуля) латинским («M001K») для ~24 артикулов;
`scripts/merge-latin-cyrillic-models.ts` переименовал эти `ProductModel` в
канонический латинский код. Ещё 2 артикула из файла плана поставки (М001Е,
М025) в эту таблицу не попали, но оказались пустыми дублями уже
существующих `M001E`/`M025` из старого реестра — их записи плана поставки
перенесены на существующую модель, дубль удалён. Остальные новые артикулы
из файла плана (М023, М030, М039, М040, М044, М054, М055 — без совпадения
в старом реестре) заведены как есть, латиницей не переименовывались, т.к.
пары для них нет.

Ещё 3 пары («М001К»/«M001K», «МОО2»/«M002», «МОО3»/«M003») обнаружились
позже — в отличие от первой волны, тут с обеих сторон была реальная
история (ТЗ, остатки готовой продукции), так что `scripts/merge-remaining-
model-dupes.ts` не просто переименовал, а слил: заказы/план/BOM
переставлены на латинскую модель, остатки готовой продукции объединены
средневзвешенно (не отброшены). Итог: 71 артикул → 68.

**Сырьё FW26 переведено на русский.** Отчёт по закупке FW26 — на
английском (международная аукционная документация), и `import-fw26.ts`
изначально завёл 54 материала с английскими названиями (напр. «SWAKARA
WHITE REG_FLAT_SILV», «Sable wild raw Barguzinsky Silvery XXL 7-1.2
SIL.3»). `scripts/translate-materials-ru.ts` переименовал их на русский
(«Свакара (каракуль) белая, REG FLAT SILV», «Соболь баргузинский дикий
серебристый сырец XXL 7-1.2 SIL.3»), при этом аукционные коды сортности
(SIL.1-6, C1/C2, VELV1/2, классы XXL/XL, буквенно-числовые классы вроде
«2-1.1») оставлены как есть — это международная отраслевая нотация, которую
русские меховщики тоже используют без перевода (например, «SWAKARA NUT»
уже встречается нетронутым в самом исходном реестре пользователя), и
гадать с их переводом рискованнее, чем оставить как есть.

**Справочник сырья унифицирован до базовых категорий меха** (по просьбе
пользователя — «MINK, FOX и так далее»). Импорт заводил отдельный
`RawMaterial` на каждый цвет/сорт/аукционный код (получилось 92 варианта
норки/соболя/лисы/каракуля вместо 4 категорий). `scripts/unify-material-
categories.ts` схлопнул их до **Норка / Соболь / Лиса / Рысь / Каракуль
(свакара)** — конкретный сорт/цвет никуда не делся, он перенесён в поле
`RawMaterialLot.grade` (и `PurchaseItem.grade`) конкретной партии, что и
есть по смыслу схемы: себестоимость и деталировка всегда были на уровне
лота, а не каталога сырья, так что это чистое упрощение справочника без
потери точности расчёта. Подкладочные ткани (это разные полотна, а не
сорта одного меха) и служебный «Сырьё (не указано)» не трогались. Итог:
105 материалов → 13.

**Поставщик — только ООО «Веллмех».** Пользователь поправил более раннее
предположение: Союзпушнина/SAGA/FH/РП и т.д. — это не наши поставщики, а
аукционы, у которых «Веллмех» закупает сырьё по нашему поручению.
`scripts/consolidate-supplier-vellmex.ts` перенёс все 49 закупок на
единственного поставщика «ООО «Веллмех»» и удалил остальные записи —
какой именно аукцион/сессия стоит за конкретной закупкой, по-прежнему
видно в `Purchase.auctionSession` (ничего не потеряно, просто это не
отдельный поставщик).

**Детализация себестоимости лота — «из чего и как получилась цена».**
Для лотов сезона FW26 в исходном отчёте была полная раскладка расчёта
(аукционный сбор, брокерская комиссия %, курс инвойса и курс ЦБ,
выделка/крашение/стрижка, аванс на таможню, комиссия агента, доставка и
т.д.) — раньше от неё бралась только итоговая цифра. Теперь она хранится
целиком в `RawMaterialLot.costBreakdown` (JSON, список `{label, value}` —
`scripts/attach-lot-cost-breakdown.ts`, 157 лотов) и раскрывается на
`/lots` по ссылке «Как получилась цена →» рядом с себестоимостью лота.
Компоненты — в исходных единицах отчёта ($, ₽, %, курс), без принудительного
пересчёта в одну валюту (сама формула многоступенчатая, и подгонять её
под красивую сумму означало бы досочинять то, чего нет в источнике).
Для лотов основного реестра (не FW26) такой детализации в источнике не
было — там показывается только финальная себестоимость, без ссылки.

Подробности и обоснование решений — в шапке `prisma/schema.prisma`.

**Важно:** мультитенантность реализована на уровне приложения (каждый запрос
фильтруется по `organizationId` из сессии), а не через PostgreSQL Row-Level
Security. Для дополнительного уровня защиты при росте продукта стоит
рассмотреть RLS.

  `https://your-domain.ru`)

## Задолженность заказчиков (дашборд)

Симметрично уже существующей «Задолженность поставщикам» добавлена карточка
«Задолженность заказчиков» — сколько клиенты должны за выполненную
давальческую работу (ТЗ). К оплате = `clientWorkPricePerUnit × количество`
(фактически произведённое, если оно есть, иначе плановое) — то же поле и то
же правило, что уже использовались на странице самого ТЗ. Оплачено — сумма
`ProductionPayment`, привязанных к клиенту. ТЗ без указанной стоимости работ
в расчёт не включаются (не выдумываем цену), а помечаются отдельной
пометкой у имени клиента.

**Важная находка (изначальная)**: у всех 159 импортированных ТЗ `clientId`
не заполнен — у 158 из них есть реальная `clientWorkPricePerUnit` из
источника (значит, это давальческая работа), но исходный лист «Реестр
(единый)» не содержит столбца с именем заказчика/покупателя вообще
(проверены все подписанные столбцы шапки — их нет). Поэтому карточка
изначально пустовала — не из-за бага, а потому что этот конкретный лист
не даёт связать ТЗ с клиентом напрямую.

**Обновление**: пользователь загрузил реальный файл-приложение
(«ПРИЛОЖЕНИЕ 141 (М001К соболь - 2 шт.)+.docx» — тот самый документ, на
который ссылается колонка «Источник файл»). Сверка подтвердила: это
подписанное Приложение к Договору подряда, и в нём прямо указан
Заказчик — **«ООО «Меркури Мода»»** (подписант Павлов А.М.) — то есть эта
запись `Client`, которую я раньше пометил как вероятный тестовый мусор
(не создана ни одним скриптом импорта, ни к одному заказу не привязана),
на самом деле **настоящий заказчик из источника**, просто заведён вручную
раньше в сессии, до того как нашёлся подтверждающий документ. Удалять её
было бы ошибкой — хорошо, что этого не сделал.

Сверка этого документа с ТЗ №141 (`П-2026-0150` в базе) построчно
совпала: все 14 лотов соболя (31, 32, 337, 343, 344, 346, 353, 1316, 1330,
1337, 1351, 1353, 1360, 1386) и их количества, стоимость работ
(246 000 ₽/ед.), материал, подкладка, плановое количество — всё сошлось
один в один с уже импортированными данными. По найденному документу
дозаполнены `clientId` («ООО Меркури Мода»), `contractNumber` («Договор
подряда № 1605 от 16.05.2025 г.») и `workOrderDate` — скрипт
`scripts/attach-tz141-source-appendix.ts`.

**Не тронуто, требует внимания**: собственные цифры документа в разделе
«ЗАКАЗЧИК ПЕРЕДАЛ» (стоимость сырья без НДС по каждому лоту) стабильно на
~5,73% выше, чем `RawMaterialLot.materialCostExclVat` в базе для тех же
лотов (проверено на 4 лотах — соотношение одинаковое, не случайный
разброс). Похоже на разные даты фиксации курса USD/РУБ между этим актом
передачи давальческого сырья и накладной закупки, на которую опирается
себестоимость в приложении — не стал перезаписывать себестоимость,
посчитанную от реальной закупки, документом с потенциально другой датой
курса. Если у пользователя есть остальные файлы `ПРИЛОЖЕНИЕ N (...).docx`
для других ТЗ — та же сверка и дозаполнение заказчика возможны по каждому
из них.

## Остаток к оплате по ТЗ (страница заказа)

Карточка «Оплаты от заказчика» на странице самого ТЗ (`/production/[id]`)
уже показывала стоимость работ, оплачено и остаток по этому заказу — это
существовало ещё до карточки на дашборде и использует ту же формулу
(`clientWorkPricePerUnit × фактически произведённое или плановое`). Разница
в источнике «оплачено»: дашборд суммирует `ProductionPayment` напрямую по
`clientId`, а страница ТЗ суммирует платежи через `ProductionPaymentOrder` —
привязку платежа к конкретным заказам (один платёж может покрывать
несколько ТЗ одного клиента, см. форму оплаты и колонку «Также покрывает» в
таблице платежей).

Именно поэтому «Оплачено» на странице ТЗ — валовая сумма всех платежей,
которые затрагивают этот заказ, без попытки разделить платёж, покрывающий
несколько ТЗ, пропорционально между ними: в кодовой базе нет такого
механизма, а придумывать пропорцию значило бы нарушать золотое правило
проекта. Когда среди платежей есть хотя бы один такой «общий» (покрывающий
и другие ТЗ того же клиента), заголовки «Оплачено» и «Остаток к оплате»
получают пометку, а под карточками появляется поясняющий текст, что остаток
приблизительный, а не точный. Пока ни у одного из 159 импортированных ТЗ не
проставлен `clientId` (см. находку выше), эта карточка нигде не отображается
на реальных данных — она сработает, как только `clientId` будет проставлен
вручную через форму заказа или появится реальный источник связи.

## Сырьё и ткани — аналитический фильтр по закупкам (`/raw-materials`)

Отдельная страница поверх уже импортированных и сверенных данных (никакого
нового парсинга источников, см. раздел «Массовое заведение данных» и сверку
ниже) — не дублирует `/lots` («Остатки и архив сырья»), а даёт срез именно
для анализа того, как сложилась цена конкретных партий.

Три независимых фильтра, каждый — **множественный выбор** (чекбоксы, не
одиночный `<select>`):

- по аукциону/сессии закупки (`Purchase.auctionSession` — «FH 06-26»,
  «СП 03.25» и т.п.);
- по виду сырья (`RawMaterial` — тот же список из 13 позиций, что и везде в
  приложении после консолидации дублей);
- по номеру лота (`RawMaterialLot.lotNumber`) — их 432, поэтому список идёт
  с текстовым фильтром над чекбоксами (`searchable-checkbox-list.tsx`),
  который просто скрывает несовпадающие строки на клиенте — сама форма
  обычный `GET`, без чекбоксов ничего не отправить нельзя, JS нужен только
  для поиска по списку.

Фильтры комбинируются через **И** (аукцион И сырьё И лот, если задано
несколько значений внутри одного фильтра — они через ИЛИ). Состояние
фильтров живёт в query-параметрах (`?auction=...&material=...&lot=...`,
каждый может повторяться), как и на `/lots` и `/production` — результат
можно сохранить в закладки или переслать ссылкой.

Результат — таблица лотов (сырьё, лот, сорт/цвет, получено/остаток,
себестоимость за ед. без НДС/НДС/итого, аукцион, ссылка на закупку, дата
поступления) плюс сводка сверху (число лотов, куплено всего, стоимость с
НДС по всей выборке).

Ниже — вторая таблица, специально под запрос «горизонтальной детализации
того, как получилась финальная цена»: одна строка на лот, но, в отличие от
сворачиваемого тоггла на `/lots` (`cost-breakdown-toggle.tsx`, там весь
расчёт лота открывается/закрывается одной кнопкой под каждой строкой), тут
каждая составляющая расчёта из `RawMaterialLot.costBreakdown` — свой
столбец, так что несколько лотов сравниваются построчно бок к боку.
Набор столбцов — объединение меток (`label`) всех `items` по всем лотам
выборки (разные сезоны отчётов поставщика добавляли разные составляющие —
аукционный сбор, % брокера, выделка, таможенный аванс, комиссия агента,
доставка и т.д.); у лота, где такой составляющей не было, ячейка просто
пустая. Курсы (`exchangeRateInvoice`/`exchangeRateFixed`) показаны отдельными
столбцами, если хотя бы у одного лота выборки они есть. Таблица может
получиться широкой — это ожидаемо (аналитический вид, не сводка), прокрутка
горизонтальная, данные не обрезаются. Показываются только лоты выборки, у
которых `costBreakdown` заполнен (329 из 432 по всей базе после двух
проходов backfill — см. записи коммитов про backfill costBreakdown).

## Переключатель «С НДС / Без НДС»

Один тумблер в шапке (`src/components/vat-toggle.tsx`, рядом с именем
организации и «Выйти») переключает, какую версию суммы показывает
компонент `<Money incl={...} excl={...} />` по всему приложению — с НДС
(по умолчанию) или без. Выбор хранится в cookie `vatDisplay`
(`src/lib/vat-display.tsx`), читается в серверном `AppLayout` при первом
рендере (без «мигания» на клиенте) и живёт в React-контексте — сам
переключатель ничего не пересчитывает и не делает round-trip на сервер,
он только выбирает, какую из двух уже правильно посчитанных на сервере
цифр показать.

**Принцип:** `incl`/`excl` для `<Money>` всегда считаются из реальных
хранимых полей (никогда не «текущая ставка НДС на глобальную сумму»).
Где корректно разделить нельзя без придумывания — компонент получает
только `incl`, и в режиме «Без НДС» показывает эту же цифру с меткой `*`
(title-подсказка), а не гадает.

**Как выведен корректный «без НДС» лот/заказ (stored-at-receipt vs.
computed-live):**
- `RawMaterialLot.unitCost` (себестоимость лота) — VAT-инклюзивная величина,
  зафиксированная при приёмке (см. схему). Её раскладка на «без НДС» уже
  частично хранилась (`materialCostExclVat`/`materialVatAmount` — только
  сырьё, без аллокации расходов). Этой правки не хватало для полной
  картины: `receivePurchase` аллоцирует пул расходов закупки на позиции
  одним и тем же коэффициентом (доля позиции в общей сумме позиций с НДС),
  а раскладку этого коэффициента на «без НДС»/«НДС» саму никуда не
  сохранял. Добавлены два новых поля — `RawMaterialLot.expenseCostExclVat`
  и `expenseVatAmount` (миграция `lot_expense_vat_split`) — и они
  заполняются **при приёмке** тем же коэффициентом, применённым к
  собственным «без НДС»/«НДС»-частям пула расходов. Это не приближение:
  раз коэффициент применяется к пулу расходов целиком одинаково, то
  `коэфф*без_ндс + коэфф*ндс = коэфф*с_ндс` — тождество, а не оценка.
  `lotUnitCostExclVat()` в `src/lib/purchase-totals.ts` = `materialCostExclVat
  + expenseCostExclVat`.
- Правка позиции закупки после приёмки (`updatePurchaseItem`, пока лот не
  тронут производством) пересчитывает и эту раскладку тем же способом —
  держит старую аллоцированную сумму расходов (и её «без НДС»/«НДС» доли)
  фиксированной, как и раньше держала саму сумму.
- Существующие 432 лота в базе на момент этой правки backfill не менял:
  в базе пока нет ни одной `PurchaseExpense` (проверено), так что у всех
  лотов `expenseCostExclVat`/`expenseVatAmount` корректно остаются 0 —
  скрипт `scripts/backfill-lot-expense-vat-split.ts` идемпотентен и пересчитает
  их из `Purchase.expenses`, если/когда расходы появятся на исторических
  закупках.
- `ProductionOrder.materialCost` (VAT-инклюзивный, из
  `ProductionMaterialUsage.totalCost` = `quantity * lot.unitCost`) —
  его «без НДС»-версия **не хранится отдельным столбцом**, а считается
  **живьём** (`materialCostExclVat()` в `purchase-totals.ts`) из тех же,
  уже зафиксированных исторических строк `materialUsages` + их лотов —
  это безопасно даже для `COMPLETED` заказа, потому что сами строки
  usage неизменны после фиксации. Выбор «считать живьём», а не хранить
  снимок — по аналогии с тем, как уже устроен `syncCompletedOrderCost`
  (то есть третий подход не придумывался).
- `ProductionExpense.amount` — в схеме у этой модели **нет поля `vatRate`
  вообще** (НДС по производственным расходам не отслеживается). Разложить
  его на «без НДС» было бы чистой выдумкой, поэтому `<Money>` для
  произв. расходов получает только `incl` — цифра одинаковая в обоих
  режимах тумблера.
- `FinishedGoodsStock.avgUnitCost` (себестоимость остатка готовой
  продукции на складе) — скользящая средневзвешенная, намешанная из
  множества завершённых заказов и корректировок за всё время; у неё нет
  сохранённой раскладки «без НДС» по каждому вкладу в среднюю, и
  разложить её сейчас без выдумывания невозможно. Показывается только с
  НДС в обоих режимах.

**Что покрыто тумблером:**
- `/purchases` — список (колонка «Сумма», строки закупки подкладки) и
  карточка закупки (сумма позиции, сумма расхода, итоговая сводка
  «Итого»).
- `/lots` — стоимость остатка (сводный отчёт по материалу, разбивка по
  складам) и итоговая (жирная) цифра себестоимости лота в архиве.
- `/dashboard` — KPI «Стоимость остатков сырья», «Закупок за 6 мес.»,
  «Сырья закуплено, всего», «Сырья использовано в производстве» и таблица
  «куплено/использовано/остаток по материалам».
- `/production/[id]` — карточки «Стоимость сырья», «Итого себестоимость»,
  «Себестоимость» (в блоке заказчика), «Себестоимость за ед.» и колонка
  «Себестоимость» в таблицах списания сырья/подкладки.

**Что НЕ покрыто (осознанно, честно оставлено с НДС):**
- `FinishedGoodsStock.avgUnitCost` и всё, что от него зависит —
  «Стоимость готовой продукции» на дашборде, `/finished-stock`,
  `/articles` (см. объяснение выше).
- Производственные расходы (`ProductionExpense`) — нет `vatRate` в схеме.
- Деньги, которые уже физически перечислены («Оплачено», «Остаток к
  оплате», «Долг поставщикам», «Долг заказчиков», выручка от заказчика
  `clientWorkPricePerUnit`, розничная цена/маркап) — это фактические суммы
  оплаты/выручки, а не расчётная себестоимость с известной ставкой НДС;
  переключать их «без НДС» означало бы придумывать ставку, которой нет в
  данных, поэтому они везде показывают одну и ту же (реальную) цифру
  независимо от тумблера.
- График «Закупки по месяцам» на дашборде — остался с НДС (сумма по
  `purchaseTotalInclVat`), не переключается.
- `/articles`, `/finished-stock`, `/models`, `/clients` и другие
  денежные показатели за пределами четырёх приоритетных страниц выше —
  не тронуты в этом проходе.

## Подкладка как отдельный раздел, прямое создание сырья, пикер ткани на ТЗ

Три доработки по итогам консолидации подкладочных лотов в один пул на ткань
(см. коммит про консолидацию лотов подкладки):

- **`/lining`** — новый верхнеуровневый раздел («Подкладка» в меню, блок
  «Закупки и склад»), отдельный от `/purchases`/`/lots`/`/raw-materials`.
  Для каждой из 7 тканей: куплено всего, использовано, остаток, себестоимость
  за ед. (без НДС / НДС / всего, через тот же тумблер и `<Money>`, что и
  везде), явный флаг «Остаток исчерпан» когда остаток ≤ 0 (без придуманного
  процента «мало» — только однозначный сигнал), какие закупки/лоты пополнили
  пул и раскрытие `costBreakdown`, если оно есть у лота (переиспользован
  `CostBreakdownToggle` из `/lots`). Карточки подкладки на `/lots`,
  `/purchases` и `/purchases/[id]` остались как есть (свой контекст), но
  теперь ссылаются на `/lining` («Смотреть все ткани →») как на канонический
  «дом» вопросов по ткани.
- **«+ Добавить сырьё»** — оказалось, что прямой CRUD для `RawMaterial`
  (`/materials`, `createMaterial`) уже существовал, но не был виден ни в
  одном меню и ни на одной странице склада — единственным способом завести
  новый материал было вставить нераспознанное имя в массовую загрузку
  позиций закупки. Добавлены видимые кнопки: «+ Добавить сырьё» на `/lots`
  (ведёт на `/materials/new`) и «+ Добавить ткань» на `/lining` (ведёт на
  `/materials/new?unit=M`, где `?unit=` просто предвыбирает единицу
  измерения в форме).
- **Пикер подкладки при создании ТЗ** — на `/production/new` рядом с полем
  свободного текста «Подкладка (описание из ТЗ)» (оставлено как есть — это
  реальные исходные данные из текста ТЗ) добавлены настоящий `<select>` по 7
  тканям (с текущим остатком в подписи каждого варианта, напр. «…№24 —
  остаток 0 м») и поле метража. Если оба заполнены, списание из пула ткани
  происходит сразу при создании заказа, в той же транзакции, что и само
  создание ТЗ: если запрошенный метраж больше остатка, транзакция откатывает
  и заказ вообще не создаётся, с ошибкой вида «недостаточно ткани «№24»:
  остаток X м, запрошено Y м» (тот же формат сообщения, что у существующей
  проверки списания сырья на странице заказа). Списание использует ту же
  функцию `consumeFromLot`, которой пользуется ручное списание на странице
  заказа — не отдельная копия логики, только автоматический перебор лотов
  ткани от старых к новым (как у автосписания по норме), если пул почему-то
  разбит на несколько лотов.

## Остатки сырья: без разбивки по складам, с разворачиванием на лоты

`/lots` («Остатки и архив сырья») переработан по прямой обратной связи:

- **Убрана разбивка «по складам»** и для меха, и (раньше) для подкладки —
  склад всего один («Склад»), поэтому такая разбивка была просто
  дублированием строки материала без всякой добавленной информации.
- **Итоговый отчёт по меху теперь разворачивается**: клик по строке
  материала (`<details>`, без JS) показывает список его лотов с полной
  детализацией (лот, сорт/цвет, получено/остаток, себестоимость без
  НДС/НДС/всего, поставщик и закупка, дата, использовано в каких ТЗ) —
  раньше это был один длинный плоский список лотов под отдельным
  заголовком «Архив лотов меха», никак не привязанный к строке материала
  над ним.
- **«Архив лотов подкладки» убран целиком** — после консолидации подкладки
  в один агрегированный лот на ткань (см. раздел выше) там оставалась одна
  строка на ткань, то есть точное дублирование «Итогового отчёта по
  подкладке» прямо над ним. Подробности по каждой ткани (куплено,
  использовано, какие закупки её пополнили, детализация себестоимости) —
  на странице [«Подкладка»](#подкладка-как-отдельный-раздел-прямое-создание-сырья-пикер-ткани-на-тз)
  (`/lining`), на которую страница остатков теперь просто ссылается.

## «Сырьё (не указано)» — было реальным сырьём, не пустой категорией

Проверка боевых данных выявила материал «Сырьё (не указано)» (141 куплено
/ 135 использовано / 6 остаток, 60 000 ₽) — сопоставление с исходным
реестром показало, что оба его лота (5020, 300302) в листе «остатки»
прямо подписаны как «Шкура норка белая, отбеленная 20», категория
«Норка», а 2 из 4 ТЗ, что его использовали, несут в самом тексте ТЗ
описание материала «Норка белая». Это не была честно неопознанная
категория — просто не смапилась на существующий материал «Норка» при
первом импорте. Объединено скриптом `scripts/merge-unspecified-into-norka.ts`
(лоты, позиции закупки, списания, движения склада и нормы BOM
переприкреплены на «Норка», сорт/цвет проставлены по тексту источника,
пустая категория удалена) — придумывать материал не пришлось, ответ был в
самом реестре.

## Сквозной аудит разделов: что проверено, что исправлено

После серии изменений в этой сессии (переключатель НДС, консолидация
подкладки, слияния материалов/моделей, фикс нумерации) проведена
проверка всех разделов, кроме `/production/*` и `/purchases/*` (там
параллельно работают другие агенты), на внутреннюю согласованность цифр
и на то, что каждая страница одинаково уважает переключатель
«С НДС / Без НДС».

**Найдено и исправлено:**

- **`/articles` («Товар и цены») не реагировал на переключатель НДС.**
  Себестоимость за единицу считалась через `formatMoney()` напрямую —
  единственная страница с суммой себестоимости, которая не подключена к
  `<Money>`, хотя `/lots`, `/lining`, `/production/[id]` и дашборд это
  давно делают. Добавлен расчёт excl-VAT части (по тем же
  `materialUsages`/`lot.materialCostExclVat`/`expenseCostExclVat`, что и
  `production/[id]`, так как отдельного excl-VAT снапшота для
  `unitCost` в схеме нет) и подключён `<Money>`. Проверено на реальных
  данных: для модели с завершённым заказом средняя себестоимость с НДС
  17 294,04 ₽, без НДС 14 175,44 ₽ — соотношение соответствует ставке
  НДС по лоту.
- **`/raw-materials` («Сырьё и ткани»): та же таблица «Себест. за ед.
  (без НДС / НДС / всего)», что на `/lots` и `/lining`, но колонка
  «всего» и итоговая колонка в таблице разбора себестоимости были
  захардкожены на `formatMoney(l.unitCost)` — без НДС не переключалось.
  Приведено к тому же виду, что на `/lots`/`/lining`:
  `<Money incl={l.unitCost} excl={lotUnitCostExclVat(l)} />`.
- **`/clients` и `/finished-stock` не было в боковом меню и никто на них
  не ссылался** — обе страницы полностью рабочие (карточка заказчика с
  давальческим биллингом; списание и лента движений готовой продукции),
  но попасть на них можно было только вводом URL вручную. Добавлены в
  раздел «Производство» бокового меню.

**Проверено, проблем не найдено:**

- **Дашборд** — все KPI и таблицы пересчитаны из тех же источников
  построчно (сверено на реальных данных: сумма остатков сырья по
  материалам совпадает с KPI-карточкой; долг заказчиков/поставщиков
  считается из тех же полей, что и на детальных страницах). НДС-toggle
  подключён везде, где для суммы есть корректный excl-VAT разбор;
  `avgUnitCost` готовой продукции и себестоимость по давальческим
  заказам осознанно показаны только с НДС — по ним нет excl-VAT
  снапшота (см. комментарии в коде).
- **`/models`** — 66 моделей, дублей по имени (кириллица/латиница) нет,
  строк BOM, ссылающихся на неактивные/слитые материалы, нет — слияния
  материалов этой сессии прошли без «осколков» в нормах расхода.
- **`/supply-plan`** — не зависит от полей, тронутых консолидацией
  подкладки/слияниями материалов (только `SupplyPlanEntry` +
  `ProductModel`), крашей и точек с устаревшими предположениями не
  найдено.
- **`/clients`, `/suppliers`, `/payments`** — CRUD-страницы простые и
  симметричные, все ссылки корректны (кроме отсутствия самой ссылки в
  меню, см. выше).
- **`/lining`** — сверено с `/lots`: все 7 тканей полностью
  израсходованы (`quantityReceived` = сумма `usages.quantity` до цента
  на каждой из 7), несовпадений нет.
- **`/settings`** — все 4 ссылки (`/materials`, `/warehouses`,
  `/expense-categories`, `/users`) ведут на существующие страницы.

**Рекомендации на будущее (не сделано в рамках этого аудита — не баги,
а отсутствующий функционал):**

- На `/raw-materials` итоговая карточка «Стоимость закупки» показывает
  только сумму с НДС (честно подписано как «(с НДС)», так что это не
  вводит в заблуждение) — можно добавить и без-НДС вариант через
  `<Money>` для единообразия с остальными карточками страницы.
- Дашборд и карточка заказа не дают ссылку на `/finished-stock` —
  теперь страница хотя бы есть в меню, но прямая ссылка с KPI
  «Стоимость готовой продукции» была бы удобнее.

## Что дальше (не реализовано в этой версии)

- Приглашение пользователей по email (сейчас владелец/админ создаёт учётку
  и передаёт пароль лично)
- Генерация печатной формы ТЗ (docx/PDF) из производственного заказа —
  данные для неё (заказчик, договор, номер ТЗ, состав сырья по лотам) уже
  есть в модели, самого рендеринга документа пока нет
- Биллинг/тарифы для продажи как SaaS другим компаниям
- Postgres Row-Level Security как второй уровень изоляции тенантов
- Автоматическое подтягивание курса валют (сейчас курс вводится вручную на
  каждую закупку — так и было решено, но при желании можно добавить
  интеграцию с ЦБ РФ)
- Розничная цена/маркап пока только на уровне производственного заказа
  (конкретной партии), не привязаны к каналу продаж (как отдельная цена
  «для ЦУМ» в примере пользователя) — можно добавить как отдельную
  сущность, если нужно вести несколько прайсов на одну модель одновременно.
  **Уточнение по итогам сверки листа «Расчет для ЦУМ»:** сам этот лист не
  подтверждает, что такая отдельная цена вообще где-то фиксировалась — он
  содержит только себестоимость лота (та же цифра, что уже импортирована
  как `unitCost`), без отдельной колонки под цену/канал «ЦУМ». Так что этот
  пробел остаётся открытым не из-за упущения при импорте, а потому что
  подходящего источника для него в файлах пользователя пока не нашлось —
  если у пользователя есть отдельный прайс-лист для ЦУМ, нужен именно он.
