# МехУчёт (fur-erp)

Мультитенантное веб-приложение для учёта закупок сырья, остатков, производства
и себестоимости. Каждая компания-клиент (Organization) видит только свои
данные; пользователи внутри компании имеют роли (владелец, администратор,
закупщик, кладовщик, технолог, бухгалтер, наблюдатель).

## Стек

- Next.js 16 (App Router, TypeScript) + Tailwind CSS
- PostgreSQL + Prisma ORM
- Auth.js (next-auth v5), учётные данные по email/паролю, JWT-сессии
- Recharts для дашборда

## Массовое заведение данных

Реальные закупки/ТЗ пользователя — это не 1-2 позиции, а обычно 10-160+ строк
за раз (см. импортированный реестр). Заполнять их по одной через форму
неудобно, поэтому на двух самых «многострочных» экранах, помимо обычной
формы на одну позицию, есть вставка сразу нескольким строками — как
скопировать из Excel и вставить:

- **Закупка → «Позиции сырья»**: вставить строки `Материал [Tab] Кол-во
  [Tab] Цена без НДС [Tab] НДС% [Tab] Лот [Tab] Сорт [Tab] Цвет` (последние
  три необязательны). Сырьё ищется по точному названию (без учёта
  регистра); не найденное — заводится автоматически как новое `RawMaterial`
  (единица измерения по умолчанию — «шт.», поправить потом на странице
  сырья).
- **ТЗ → «Списание сырья в производство»**: вставить строки `Лот [Tab]
  Количество` — лот ищется по номеру на складе сырья этого заказа. Строки,
  которые не удалось разобрать (лот не найден, не хватает остатка,
  нечисловое количество) — не пропадают молча, а перечисляются под формой,
  остальные всё равно применяются.

## Модель данных (кратко)

`Organization` → `User` (роли) · `Supplier` → `Purchase` (валюта +
`exchangeRate`, курс вводится вручную на дату сделки) → `PurchaseItem`
(цена в валюте закупки, опциональный номер лота) + `PurchaseExpense` +
`Payment`. При оприходовании: цена позиции конвертируется в рубли по курсу
закупки, доп. расходы (всегда в рублях) распределяются на позиции
пропорционально сумме — вместе это даёт себестоимость лота.

**Партионный учёт сырья (specific identification), не средневзвешенный.**
Каждая закупленная партия — отдельный `RawMaterialLot` с фиксированной на
дату поступления себестоимостью за единицу. Производство списывает сырьё с
конкретного лота по его цене (`ProductionMaterialUsage.lotId`), а не из
общего пула — потому что цена одной шкурки в разных лотах может отличаться
в разы. «Остатки по материалу» на дашборде и странице склада — это
агрегат по лотам на лету, не отдельно поддерживаемый кэш.

**НДС по каждой позиции своя ставка.** `PurchaseItem.vatRate` и
`PurchaseExpense.vatRate` хранятся отдельно на каждой строке — ставка,
действующая на дату сделки, реально меняется (в одном и том же реестре
пользователя встречаются и 20%, и 22%). Цена/сумма вводятся без НДС, при
оприходовании НДС начисляется сверху и попадает в себестоимость лота
(`RawMaterialLot.unitCost`); `materialCostExclVat`/`materialVatAmount`
хранят разбивку just сырьевой части для детализации. Общий расчёт «сколько
реально стоит закупка» — `src/lib/purchase-totals.ts`, переиспользуется
списком закупок, карточкой закупки и дашбордом, чтобы не разъезжались.

**Архив сырья** (`/lots`, объединён с бывшей страницей «Остатки») —
сводка по материалу вверху + полная история всех лотов (не только остаток
> 0), с поиском по номеру лота/материалу/цвету/сорту и ссылками на закупку
и на производственные заказы, где лот был использован («Использовано в») —
чтобы можно было найти и «подтянуть» нужную партию при планировании ТЗ.
Закупка также хранит `auctionSession`/`invoiceNumber`/`transferDocument`
(аукцион/сессия, № счёта, УПД) — как реально оформляется закупка на
пушном аукционе.

`ProductModel` + `ProductModelMaterial` (норма расхода, BOM) →
`ProductionOrder` — карточка ТЗ, поля 1:1 с примером пользователя
(материал продукции, подкладка, опционально `Client`-заказчик, номер
договора подряда, № и дата ТЗ, стоимость работ за ед.). Списание сырья —
по конкретным лотам (с текстовым поиском по номеру/цвету/сорту, т.к. лотов
может быть много), одной кнопкой «по норме BOM», или вставкой сразу
нескольких строк «Лот [Tab] Количество» (см. «Массовое заведение» ниже) —
накапливает
`ProductionExpense`; при завершении заказа себестоимость фиксируется и
создаётся приход на склад готовой продукции (`FinishedGoodsStock`,
средневзвешенная — тут разброс себестоимости не критичен). Отдельно —
розничная цена за единицу и автоматический маркап = розничная цена /
себестоимость.

**Проверено на реальном примере ТЗ №141** пользователя (14 позиций сырья
по 2 материалам, ставка НДС 22%, поставщик «Союзпушнина», лоты 31–1386):
себестоимость сырья сошлась с оригиналом ТЗ с точностью до рубля при первой
сверке. После массового импорта всего реестра (см. ниже) эти же 14 лотов
оказались общими ещё с 4 другими производственными заказами из реестра
(лот может быть распределён на несколько ТЗ) — их себестоимость теперь
считается по цене лота из сводного реестра «остатки», а не только из этого
одного ТЗ, поэтому итоговая цифра (`П-2026-0150`, ≈7,64 млн ₽ на 2 шт.)
немного отличается от изначально сверенной вручную (была ≈8,10 млн ₽) —
разница в основном из-за подкладки, которая в реестре для этого конкретного
ТЗ не была найдена парсером (раздел реестра начиная примерно с ТЗ №88
использует другую раскладку колонок) — см. следующий раздел.

**Массовый импорт всего реестра сырья и ТЗ.** По просьбе пользователя внесены
все лоты и все производственные заказы из его реального файла
(`21-08 ЕДИНЫЙ_РЕЕСТР_ПО_МЕХУ_MVST 2.xlsx`, листы «остатки» — сводка по
партиям с суммой/аукционом/счётом/УПД — и «Реестр (единый)» — по каким ТЗ
и в каком объёме списан каждый лот): 3 поставщика, 50 видов сырья,
32 закупки, 274 лота, 65 артикулов, 159 производственных заказов
(510 шт. готовой продукции). Импорт сделан скриптом
`scripts/import-registry.ts` (запуск: `node --env-file=.env
node_modules/.bin/tsx scripts/import-registry.ts`) по данным, заранее
извлечённым и сгруппированным Python-скриптами (не входят в репозиторий) в
`scripts/import_plan.json`; скрипт идемпотентен — повторный запуск
пропускает уже созданные закупки/заказы (метка в поле `notes`).

Импорт использует ту же бизнес-логику, что и обычные действия приложения
(создание лота, списание с лота, приход на склад готовой продукции), но в
реестре не хватало части данных, поэтому пришлось сделать допущения —
**их стоит перепроверить**:

- **Ставка НДС 22% для всех импортированных лотов.** В реестре нигде не
  указана ставка по конкретному лоту (только итоговая цена «в т.ч. НДС»);
  22% — то же значение, что подтвердилось на ТЗ №141 вручную.
- **Поставщик «РП» (аукционные сессии с кодом «РП», напр. «РП 03.25»)
  создан как отдельный поставщик с условным именем** «РП (аукцион, требует
  уточнения названия)» — в реестре встречается только сокращение, полного
  юридического названия нет. Аукционы с кодом «СП» отнесены к уже
  существующему поставщику «Союзпушнина». Лоты с пометкой «Нет информации»
  об аукционе (но с реальным номером счёта/УПД) тоже отнесены к
  «Союзпушнина» по умолчанию.
- **Про «Веллмех»:** в исходном ТЗ-документе ООО «Веллмех» — это
  ПОДРЯДЧИК (исполнитель работ, т.е. сторона пользователя), а не поставщик
  сырья, поэтому оно не заведено как `Supplier`. Если у пользователя есть
  фактический список поставщиков мехового сырья за пределами «Союзпушнина»
  и «РП» — их нужно назвать отдельно, реестр не даёт других имён.
- **Материал для 14 лотов, не найденных ни в закупках, ни разу не
  списанных ни в одном ТЗ** (не было расчётной подсказки) взят из колонки
  M/N листа «остатки» (общее название вроде «Соболь»/«Норка») — грубее, чем
  для остальных материалов.
- **Лот, использованный в нескольких ТЗ с разным описанием материала**
  (встречается — например, один и тот же лот в одном заказе назван «Соболь
  дикий выделанный», в другом «Соболь баргузинский») — категория сырья
  зафиксирована по самому раннему (по номеру строки реестра) упоминанию;
  реальная физическая партия сырья, конечно, одна.
- **Подкладочные материалы** не имеют собственных номеров лотов в реестре —
  для каждой строки списания подкладки создан отдельный технический лот
  (получено = списано), сгруппированный в одну закупку «Подкладочные
  материалы (сводно по реестру)».
- **2 строки реестра пропущены полностью**: строка-«роллап» ТЗ №88 (сумма
  по 4 дочерним заказам, которые уже учтены отдельно) и ремонт пальто по
  ТЗ №116 (нет артикула модели — акт ремонта, не производство нового
  изделия).
- Заказчик/договор подряда не заполнялись массово (в реестре их нет,
  только в отдельных docx) — все импортированные заказы отмечены как
  собственное производство, без `Client`.

**Закупка сезона FW26** (`08_06_2026_Отчет_по_закупке_мехового_сырья_MVST.xlsx`,
лист «закупка FW26») добавлена тем же способом (`scripts/import-fw26.ts` +
`scripts/fw26_plan.json`): 17 закупок, 162 позиции сырья. В этом отчёте
себестоимость уже полностью разложена по формуле (аукционный сбор, выделка/
крашение/стрижка, транспорт, растаможка, комиссии, НДС 22%) — использована
готовая итоговая цифра «Себестоимость за единицу» без пересчёта.

- **Поставщики определены по названию аукционной сессии**: «SAGA 03-26» →
  «SAGA Furs», «FH 06-26» → «Fur Harvesters Auction (FH)» (оба — реальные
  международные пушные аукционы, но названия в самом отчёте не подтверждены
  документом, а угаданы по общеизвестным названиям — стоит проверить);
  «СОЮЗПУШНИНА 05-26» — к существующему «Союзпушнина»; одна позиция явно
  ссылается на «ООО «Веллмех» СПЕЦИФИКАЦИЯ № 18...» — заведено как отдельный
  поставщик «ООО «Веллмех»» (в отличие от старого реестра, тут это явно
  контрагент по закупке, а не подрядчик); остальное («Закупка меха 04-26» —
  без названия поставщика в отчёте) — под условным поставщиком «Закупка
  мехового сырья FW26 (поставщик не указан в отчёте)».
- **4 лота уже существовали** в базе как грубая оценка (заведены только по
  тому, что было списано в производство, без данных о закупке — см. выше
  «14 лотов... остатки»): 355159, 165270, 500083, 300687. У них в отчёте
  FW26 та же цена за единицу (значит это те же самые партии) — их
  `quantityReceived`/`quantityRemaining` скорректированы до реальных цифр
  из отчёта, а не задвоены.
- **4 номера лота (30, 32, 33, 1525) и ещё 5 других совпали** с номерами
  лотов из более раннего сезона (другое сырьё, другая цена — просто
  аукционный дом переиспользует короткие номера) — заведены как новые лоты
  с префиксом `FW26-`, чтобы не путать с одноимённым лотом из прошлого
  сезона на `/lots`.

**Важный нюанс, оставленный на усмотрение пользователя:** в этой версии
производственный заказ считает маржу как «стоимость работ для заказчика
минус полная себестоимость (включая закупленное нами сырьё)» — то есть
сырьё считается нашим собственным. В реальном ТЗ раздел «Заказчик передал»
предполагает, что материал может быть давальческим (собственность
заказчика) — тогда его стоимость не должна вычитаться из выручки за
работу. Сейчас это не разделено; если нужно — можно добавить признак
«давальческое сырьё» на заказ, который исключает стоимость сырья из
расчёта маржи.

**Оплаты — отдельно по закупкам и отдельно по производству.** `Payment`
(поставщику, привязан к закупке) остался как был. Добавлен `ProductionPayment`
— отдельный учёт оплат ОТ заказчика (карточка ТЗ показывает «Стоимость
работ / Оплачено / Остаток к оплате»), не связанный с закупочными
оплатами. Одна оплата может покрывать сразу несколько ТЗ одного заказчика
— клиент часто платит одной суммой за несколько сделанных заказов, или
вносит аванс — поэтому `ProductionPayment` связан с `ProductionOrder`
через таблицу-связку `ProductionPaymentOrder` (многие-ко-многим), а не
напрямую; при добавлении оплаты на карточке ТЗ можно отметить и другие ТЗ
того же заказчика, которые она тоже покрывает. Тип оплаты — `Аванс` /
`Доплата` / `Окончательная`.

**Розничная цена — одно число на артикул, не на ТЗ.** Раньше
`ProductionOrder.retailPrice` и `ProductModel.sellingPrice` редактировались
независимо и расходились. Теперь оба поля обновляются вместе, с какой бы
страницы (карточка ТЗ или «Товар и цены») её ни поменяли: правка на любой
из двух страниц сразу проставляет цену и на модель, и на все её ТЗ, маркап
пересчитывается сам — как «ПРЦ», один параметр на артикул в исходном
экселе, а не отдельная цифра на каждую партию.

**Подкладка — отдельным разделом.** И на карточке закупки, и на карточке ТЗ
позиции разделены на «мех» и «Подкладка» (по `RawMaterial.unit === "M"` —
ткань меряется в метрах, мех в штуках, разделение уже было в данных, просто
не было в интерфейсе): отдельная форма добавления, отдельная таблица.
На ТЗ выбор подкладки при списании — тот же самый пикер лота, что и для
меха, просто в своей карточке и со списком только тканевых лотов.

**«Товар и цены»** (`/articles`) — отдельная страница со списком артикулов
(`ProductModel`), их средневзвешенной себестоимостью по завершённым ТЗ,
редактируемой розничной ценой (`ProductModel.sellingPrice`) и посчитанным
маркапом; плюс сводка сверху (кол-во артикулов, выпущено шт., стоимость по
розничным ценам). Себестоимость — ссылка на `/production?model=…`
(отфильтрованный список ТЗ этой модели), чтобы провалиться в детализацию,
из чего сложилась цифра.

**Финальный отчёт по сырью** — на `/lots` вверху и на `/dashboard` отдельным
блоком: таблица по каждому материалу (куплено всего / использовано /
остаток / стоимость остатка) с итогом по всем материалам, вместо только
разбивки по складам.

**Навигация** упрощена: «Производство» → «План поставки» → «Товар и цены» →
«Модели изделий»; «Остатки готовой продукции» и «Заказчики» убраны из меню
(страницы остались рабочими, просто без прямой ссылки — учёт по
давальческим заказчикам сейчас не в фокусе, но данные не удалены).

**«План поставки»** (`/supply-plan`, модель `SupplyPlanEntry`) — верхнеуровневая
плановая сетка: артикулы по строкам, месяцы по столбцам, независимая от
конкретных ТЗ. В каждой ячейке — одна или несколько записей (разные размеры/
партии одного артикула в одном месяце), у каждой: статус, количество,
опциональная дата события, заметка; статус редактируется инлайн. Набор
статусов (`SupplyPlanStatus`) взят из реальной таблицы отслеживания
пользователя («Копия производство на 22092026.xlsx»): Запланировано → Запуск
→ В работе у скорняка → В работе у портной → Сдано/произведено, плюс
Отменено. Это отдельный инструмент планирования, не привязанный к
списанию сырья/себестоимости конкретного `ProductionOrder` — если нужно
жёстко связать план с фактическим ТЗ (например, автоматически переводить
план в «произведено» при завершении заказа), это можно добавить отдельно.

План заполнен из реального файла пользователя (`scripts/import-supply-plan.ts`
+ `scripts/supply_plan_import.json`): там каждая строка — один экземпляр
изделия (размер) с цепочкой дат по стадиям и текстовым примечанием; статус
определён по приоритету «отменён» → «сдано» (есть дата сдачи или слово
«сдан(о/а)» в примечании) → «у портной» → «у скорняка» → «запуск» →
«запланировано», затем сгруппировано по (артикул, месяц, статус) с
подсчётом штук. 9 артикулов из этого файла (М001Е, М023, М025, М030, М039,
М040, М044, М054, М055) отсутствовали в базе — заведены как новые
`ProductModel` без BOM/себестоимости (это будущая, ещё не начатая
производством продукция).

**Путаница кириллица/латиница в кодах артикулов — устранена.** В исходном
файле реестра оказался скрытый лист «Лист16» с официальным соответствием
кириллических кодов (как их набирали в одних листах, например «МОО1К» с
кириллической «О» вместо нуля) латинским («M001K») для ~24 артикулов;
`scripts/merge-latin-cyrillic-models.ts` переименовал эти `ProductModel` в
канонический латинский код. Ещё 2 артикула из файла плана поставки (М001Е,
М025) в эту таблицу не попали, но оказались пустыми дублями уже
существующих `M001E`/`M025` из старого реестра — их записи плана поставки
перенесены на существующую модель, дубль удалён. Остальные новые артикулы
из файла плана (М023, М030, М039, М040, М044, М054, М055 — без совпадения
в старом реестре) заведены как есть, латиницей не переименовывались, т.к.
пары для них нет.

**Сырьё FW26 переведено на русский.** Отчёт по закупке FW26 — на
английском (международная аукционная документация), и `import-fw26.ts`
изначально завёл 54 материала с английскими названиями (напр. «SWAKARA
WHITE REG_FLAT_SILV», «Sable wild raw Barguzinsky Silvery XXL 7-1.2
SIL.3»). `scripts/translate-materials-ru.ts` переименовал их на русский
(«Свакара (каракуль) белая, REG FLAT SILV», «Соболь баргузинский дикий
серебристый сырец XXL 7-1.2 SIL.3»), при этом аукционные коды сортности
(SIL.1-6, C1/C2, VELV1/2, классы XXL/XL, буквенно-числовые классы вроде
«2-1.1») оставлены как есть — это международная отраслевая нотация, которую
русские меховщики тоже используют без перевода (например, «SWAKARA NUT»
уже встречается нетронутым в самом исходном реестре пользователя), и
гадать с их переводом рискованнее, чем оставить как есть.

**Справочник сырья унифицирован до базовых категорий меха** (по просьбе
пользователя — «MINK, FOX и так далее»). Импорт заводил отдельный
`RawMaterial` на каждый цвет/сорт/аукционный код (получилось 92 варианта
норки/соболя/лисы/каракуля вместо 4 категорий). `scripts/unify-material-
categories.ts` схлопнул их до **Норка / Соболь / Лиса / Рысь / Каракуль
(свакара)** — конкретный сорт/цвет никуда не делся, он перенесён в поле
`RawMaterialLot.grade` (и `PurchaseItem.grade`) конкретной партии, что и
есть по смыслу схемы: себестоимость и деталировка всегда были на уровне
лота, а не каталога сырья, так что это чистое упрощение справочника без
потери точности расчёта. Подкладочные ткани (это разные полотна, а не
сорта одного меха) и служебный «Сырьё (не указано)» не трогались. Итог:
105 материалов → 13.

Подробности и обоснование решений — в шапке `prisma/schema.prisma`.

**Важно:** мультитенантность реализована на уровне приложения (каждый запрос
фильтруется по `organizationId` из сессии), а не через PostgreSQL Row-Level
Security. Для дополнительного уровня защиты при росте продукта стоит
рассмотреть RLS.

## Локальная разработка

```bash
docker compose up db -d      # поднять только PostgreSQL
cp .env.example .env         # и поправить порт/секрет при необходимости
npm install
npx prisma migrate dev
npm run dev
```

Приложение откроется на `http://localhost:3000` (или на порту, который вы
укажете).

## Продакшен через Docker

`docker-compose.yml` поднимает и базу, и приложение. При старте контейнер
приложения автоматически применяет миграции (`docker-entrypoint.sh`) и лишь
затем запускает сервер — это безопасно повторять при каждом деплое.

```bash
NEXTAUTH_SECRET=$(openssl rand -base64 32) docker compose up -d --build
```

Обязательно задайте в окружении:

- `NEXTAUTH_SECRET` — случайная строка (см. команду выше)
- `NEXTAUTH_URL` — публичный URL приложения (например,
  `https://your-domain.ru`)
- `DATABASE_URL` — если используете внешнюю управляемую PostgreSQL вместо
  контейнера `db` из compose-файла

## Деплой на Timeweb Cloud

1. Создайте приложение/сервер с поддержкой Docker Compose (Timeweb Cloud
   Apps или обычный облачный сервер с установленным Docker).
2. Склонируйте репозиторий на сервер.
3. Создайте `.env` (или задайте переменные в панели Timeweb) как минимум с
   `NEXTAUTH_SECRET` и `NEXTAUTH_URL` (реальный домен).
4. Если используете управляемую PostgreSQL Timeweb Cloud вместо контейнера
   `db` — пропишите её `DATABASE_URL` и уберите сервис `db` из
   `docker-compose.yml` (или оставьте только сервис `app`).
5. `docker compose up -d --build` — при первом запуске автоматически
   применятся миграции и создастся схема БД.
6. Настройте домен/SSL через панель Timeweb (реверс-прокси перед
   контейнером на порту 3000).

Резервное копирование: делайте регулярные бэкапы PostgreSQL (Timeweb Cloud
предлагает managed-снапшоты; для контейнера — `pg_dump` по расписанию).

## Что дальше (не реализовано в этой версии)

- Приглашение пользователей по email (сейчас владелец/админ создаёт учётку
  и передаёт пароль лично)
- Генерация печатной формы ТЗ (docx/PDF) из производственного заказа —
  данные для неё (заказчик, договор, номер ТЗ, состав сырья по лотам) уже
  есть в модели, самого рендеринга документа пока нет
- Биллинг/тарифы для продажи как SaaS другим компаниям
- Postgres Row-Level Security как второй уровень изоляции тенантов
- Автоматическое подтягивание курса валют (сейчас курс вводится вручную на
  каждую закупку — так и было решено, но при желании можно добавить
  интеграцию с ЦБ РФ)
- Розничная цена/маркап пока только на уровне производственного заказа
  (конкретной партии), не привязаны к каналу продаж (как отдельная цена
  «для ЦУМ» в примере пользователя) — можно добавить как отдельную
  сущность, если нужно вести несколько прайсов на одну модель одновременно
